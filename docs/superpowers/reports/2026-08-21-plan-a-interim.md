## 1. 배경 — 왜 상태를 줄이는가

로봇 여러 대가 레고 모델을 조립한다. 고장·방전·통행금지구역 같은 **계획 밖 사건(OOD)** 이
터지면 무엇을 할지 골라야 한다. 그 선택 문제를 SMDP 로 적고, MCTS 가 **생성 시뮬레이터**
`G(s,a) → (s′, R, τ)` 를 샘플링해 푼다.

`s` 의 역할이 "모델을 재출발시키는 것"에서 **"트리 노드를 색인하는 것"** 으로 바뀌었으므로
**손실 압축이 허용된다.** 판정 기준(spec §2-1):

> 이미 하드코딩된 하위 정책의 관할이거나, `s` 안의 다른 값에서 다시 만들 수 있거나,
> 상수면 상태가 아니다.

그 결과가 `s = (G, Geo, Fleet, Prog)` **7필드**, 로봇당 `(soc, usage_s)` 둘이다.

### 2-4. T12 리뷰 결과 (세션 종료 직후 도착)

**Task quality: Approved**, Critical 0, Important 3 — **셋 다 앞을 향한다**(T14 가 필요로 할 것).

리뷰어가 `rvo_interface.jl` 을 통해 기전을 확인해서, T12 의 결론을 **더 강하게** 만들었다:
`deepcopy` 된 env 는 **RVO 상태를 아예 안 들고 다닌다** — id 하나를 조회 키로 쓸 뿐이다. 그리고
`rvo_rebuild!` 가 시뮬레이터와 id 맵을 **통째로 버리고 재유도**하므로, RVO 세계는 언제나 하나이고
**마지막으로 재구축된 env 의 전함수**다. 즉 "포크 전환마다 재구축"은 필요조건일 뿐 아니라
**충분조건**이다 — 보고서가 말한 것보다 유용한 진술이다.

리뷰어가 덧붙인 두 가지, 둘 다 T14 를 구속한다:
1. **낡은 읽기의 실패 모드가 갈리고 절반만 시끄럽다.** 두 포크에 다 있는 id 는 **조용히 틀리고**,
   한쪽에만 있는 id — 정확히 `Replace` 가 만드는 것 — 은 던진다. **"에러가 안 났으니 맞는 포크"로
   추론하면 안 된다.**
2. **인덱스 배정이 순회 순서를 탄다.** 두 포크의 agent 집합이 갈리면 낡은 읽기가 "다른 포크의 같은
   로봇 위치"라는 보장도 없다. 시험은 **구성이 동일한** 전환만 쟀다.

🔴 **Important 1 — `R` 의 에너지 항이 `_hz_excluded()` population 불일치를 물려받는다. 확정.**
`energy_between` 은 `keys(s.fleet)` 만 합산하는데, `s.fleet` 은 **고장 로봇**을 뺀다. 엔진 원장은
주차 예비만 빼고 **고장 로봇에게는 대기전력을 부과한다** — **고장 로봇이 바로 그 차이**이고,
그 상태는 Replace 가 치울 때까지 지속된다. 그래서 **고장 발생~Replace 사이의 모든 `generate`
전이가 `idle_W × |고장| × τ` 만큼 에너지를 과소계상한다.**

**N-G5 는 `RTOL = 1e-6` 으로 비교한다.** 0 이 아닌 어떤 불일치도 실패하고, 그게 **population 차이가
아니라 에너지 회계 버그로 읽힌다.** 같은 비교에 쐐기가 둘 더 있다: `energy_between` 은
`mode_power_W` 를 `team=1, m_payload=0, speed=v_ref` 기본값으로 부르는데 엔진은 실제 값을 쓴다.

→ **T14 를 시작하기 전에 N-G5 의 비교 대상 또는 허용오차를 다시 정해야 한다.** 안 그러면 T14 가
예산을 모델링 근사 추적에 쓴다.

🔴 **Important 2 — `generate` 가 `E` 를 버려서 `R` 이 N-G5 가 필요한 형태로 분해되지 않는다.**
N-G5 는 `Στ` 와 `ΣΔE` 를 **따로** 필요로 하는데, T14 는 `E = (-R - τ)/w_E` 로 역산해야 하고 그러려면
`objective.json` 을 다시 읽어야 한다 — 단일 진실원의 두 번째 소비처. **브리프의 4-tuple 이 강제한
손실**이라 plan-mandated 이고, 수정은 순수 추가다.

**Important 3 — M9 생존 변이의 범위 설명이 반박 가능하다.** T12 는 "T14 의 트리 루프가 있어야
의미 있다"고 했지만, 리뷰어가 **이 파일의 헬퍼만으로 다섯 줄이면 오늘 죽는다**고 구체적으로
보였다. 이 파일이 헤더에 선언한 계약 넷 중 **시험이 없는 유일한 것**이고, 하필 이 태스크의 핵심

그 밖에 리뷰가 확인해 준 것: 커밋 위생(다른 레인 편집이 커밋에 없음), `ActionRegistry` 배선이

### 2-5. C4 수정 결과 (세션 종료 직후 도착) — 프롬프트 규칙이 **세 가지로** 틀렸다

C4 는 자기 가설을 이미 한 번 죽였다(`r + work_reach` 는 충분조건이 아니다 — 강체 이동이 바깥
작업을 zone 안으로 쓸어넣는다). 수정 라운드에서 **방향과 크기를 분리해 재측정하자 두 번 더
반증됐다.**

**반증 ① — 두 e2e 런의 차이는 크기가 아니라 전적으로 방향이었다.**
`1.05·(r+work_reach) = 7.243` 을 **+x** 로 쓰면 통과하고(필요치 7.2418), `7.5` 를
`(build_center − center)` 로 쓰면 실패한다. 즉 앞서 "크기가 부족했다"고 읽었던 것이 **방향
문제**였다.

**반증 ② — 프롬프트가 지정한 방향이 그 씬에서 가장 나쁜 방향이다.**
`(build_center − center)` 로는 **19.33** 이 필요한데 천장이 **8.58** 이다 — **그 방향으로는 허용
가능한 Δ 가 존재하지 않는다.** 그리고 `colored_8x8` 에서는 두 중심이 일치해서 **규칙에 내용이
없다.**

**반증 ③ — `r + work_reach` 는 하한도 아니다.**
32 방향 전부에서 갇힌 작업은 빼내지만 zone 을 치우는 건 **2/32** 와 **16/32** 뿐이고, 진짜 최소는
그보다 **아래**다 (5.0997 < 5.1978).

→ 이제 **참조 크기**로만 서술하고, **진짜 천장**을 descriptor 에 실어 보낸다:
`max_shift = D − ‖build_center‖ − build_radius`. 그게 "여유를 두고 초과하라" vs "바로 위를
겨냥하라" 모순을 **숫자로** 닫는다.

커버리지도 한 점이 아니라 **32 방향 전수**로 복원했다 — 변이 M8(반증된 충분성 믿음을
`translate_clears_zones` 에 encode)이 정확히 `0 < 32 < 32` 에서 빨개진다. 변이 8종 전부 red.
`tools/e2e.jl mock_respec` **PASS** (`closed 0 → 279/289`), mock 이 `max_shift` 를 소비하고
`+x` 가 **하네스의 씬 고유 선택이지 유도가 아님**을 rationale 과 주석에 명시한다.

그리고 minor 수정 중 **재실행으로 진짜 버그 하나를 잡았다** — check dict 이
`Dict{String,String}` 으로 추론돼 `d["passed"] = Bool` 이 `MethodError` 를 던졌다. 시험을 다시
돌리지 않았으면 못 봤을 것이다.

### 3-1. 논리 오류 — `Disjunction` 이 ∧ 로 구현돼 있었다

계획서의 `Disjunction` `:eq` 컴파일이 `@constraint(model, l == rhs)` 였다. **논리합을 논리곱으로**
구현한 것이다. Big-M 두 줄로 재구현했다. 오타가 아니라 설계 논리 오류다.

### 3-2. spec §2-6 결함 — `mode_of` 가 λ 를 20배 틀리게 한다

spec 은 `mode` 를 `s.g.binding` 에서 유도한다고 적었다. `_responsible_robots` 는 **팀 전체**를
돌려주는데 `simstate_of` 는 `binding` 에 **한 명만** 남긴다. 그래서 나머지 팀원이 `:carry` 대신
`:idle` 로 분류되고, `mult_carry = 2.0` vs `mult_idle = 0.10` → **λ 가 정확히 20배 틀린다.**
계획서 판 `mode_of` 를 넣으면 시험 24개가 실패한다(실측).

**정정된 정의:** *어느 노드가 활성인가* 는 `s` 에서, *누가 맡는가* 는 `env.sched` 에서.
spec 에 정정 커밋 완료(`b0fc40f8`).

### 3-3. spec §4-1 결함 — D-6 는 "상한"이 아니고, 안전 방향이 반대다

계획서는 새 rate boundary 를 **"상한 근사"** 라고 적고 크기 판정을 N-G1 에 미뤘다. T8 이 **모드
상수 구간** 21개에서 재측정: over/exact/under = **4 / 11 / 6**, 평균비 **0.939** — 상한이 아니라
**순 과소추정**이다.

그리고 안전 방향이 서술과 반대다. `sample_sojourn` 은 `min(T_plan_next, …)` 까지 적분하므로
**과대추정이 위험한 방향**(실제 경계를 넘어 낡은 λ 를 씀)이고 과소추정은 보수적이다.

⚠️ 그리고 그 표의 **중앙값 1.000 은 측정값이 아니라 `dt_sim = 0.025 s` 눈금**이다 — "정확히

### 3-5. 안전 논증이 무너지는 자리 — 예외는 전이가 아니다

C2 가 `(t0, tF, Xa)` 를 LLM 에 열자, **파싱에 성공한 제약이 시뮬레이션을 죽이는** 경로가 생겼다.

금지하지 않는다.**

- 🔴 **`state_hash` 는 디렉토리/재컴파일을 건너 이식 가능한 키가 아니다.** `prog.closed` 가 **정점
  번호**를 저장하므로 **두 세계에서 같은 해시가 나오면서 실제 닫힌 작업은 다를 수 있다**(실측).
  방향이 반대인 두 실패가 동시에 난다 — 다른 세계가 병합되고, 같은 세계가 병합되지 않는다.
  → **트리는 행동 경로로 색인하고, `state_hash` 는 한 디렉토리 안의 진단으로만 쓴다.**
- 🔴 **"전/후" 측정 중 재컴파일이 끼어 있으면 코드 변화 ⊕ 세계 변화를 잰 것이다.**
- 🔴 **MCTS 는 포크할 때가 아니라 포크를 *전환*할 때마다 `rvo_rebuild!` 해야 한다** (T12 실측).
  RVO2 가 프로세스 전역 하나라 **마지막으로 재구축된 env 를 따라간다.** 갈래 비용이 갈래당이
  아니라 **노드 방문당**이라는 뜻이다.

### 7-1. D-4 가 known 세계에 zone 기전을 켠다 (실험 설계)

#### 배경 — OOD 실험의 전제

이 연구의 주장은 "정책이 학습 중에 **한 번도 못 본** 사건이 배포 중에 오면, conformal 구간
겹침이 그것을 탐지한다"이다. 그래서 사건 종류를 둘로 갈라 놓았다(CLAUDE.md §OOD):

| | 종류 |
|---|---|
| **known** (학습에 들어감) | `fault` · `battery` · `fault_battery` |
| **test-only** (배포 때 처음 봄) | `zone` · `fault_zone` · `battery_zone` · `all` |

그리고 CLAUDE.md 가 못박는 조항이 있다 — known 세계에서 빠지는 것은 **매크로가 아니라 기전
전체**여야 한다. 즉 학습 롤아웃에서는 `zone` 이라는 *행동 어휘*만 빠지는 게 아니라 **zone 이
생기는 물리 자체**가 없어야 한다. 안 그러면 정책은 zone 을 이미 겪은 것이고, "안 본 사건"이
아니다.

#### 기전 — 코드가 실제로 하는 일

`hazard.jl:520-524` 의 **함대 수준(fleet-level) zone 시계**:

```julia
λz = _rate(st.params.mtbf_zone_s) * st.params.mode
if λz > 0
    st.cum_zone += λz * dt
    st.cum_zone >= st.thr_zone && _hz_fire_zone!(env, st)
end
```

**이 블록에 에피소드 종류를 보는 조건이 하나도 없다.** hazard 가 켜져 있으면 매 스텝 돈다.
그리고 `_hz_fire_zone!` 은 주입이 실패해도 **항상 재장전**한다(`st.cum_zone = 0.0;
st.thr_zone = _exp1(st.rng_zone)`) — 에피소드 내내 zone 을 계속 만든다.

D-4 이전에는 이게 무해해 보였다. `mtbf_zone_s = Inf` 라 `λz = 0` 이었고 `if` 가 한 번도
안 열렸기 때문이다. **D-4 가 `Inf → 1800.0` 으로 바꾸는 순간 이 블록이 살아난다.**

라벨 레인도 같은 세계다 — 그리고 그건 **의도된 것**이다. T6 이 두 레인을 일부러 맞췄다:

```julia
# gen_oracle_dataset.jl:156
mtbf_zone_s = parse(Float64, get(ENV, "DS_MTBF_ZONE", "1800.0")),   # D-4: HazardParams() 기본과 일치
```

그리고 `:1027`·`:1355` 가 **kind 와 무관하게** `enable_hazard!(env; params = HZ_PARAMS,
seed = hz_seed)` 를 부른다. 즉 `fault` 롤아웃도 `battery` 롤아웃도 배경 zone 시계를 달고 돈다.

#### 크기 — 얼마나 새는가

`mode` 는 기본 `1.0` 이고 라벨 레인이 덮어쓰지 않는다. 그래서 zone 율 = `1/1800 s⁻¹`.
에피소드 makespan 이 20–35 시뮬초이므로

```
P(에피소드 안에 zone ≥ 1회) ≈ 1 − exp(−35/1800) ≈ 1.9 %
```

**대략 50 판에 1 판.** 작지만 0 이 아니고, **conformal 의 α (0.01~0.1)와 같은 자릿수**다.
탐지기의 오경보 예산과 오염률이 같은 크기면 그 실험은 무엇을 쟀는지 말할 수 없다.

#### 무엇이 깨지는가

1. 🔴 **"zone 은 안 본 사건" 전제가 조용히 거짓이 된다.** 1~2 % 의 known 판에 zone 이 들어 있다.
2. 🔴 **그 오염을 기록하는 축이 없다.** zone 을 뺀 라벨셋과 안 뺀 라벨셋은
   `objective_hash` · `vocab` · `dynamics` 가 **셋 다 같다.** 산출물만 보고는 구분이 불가능하다.
   → CLAUDE.md 가 이미 요구한 **`train_kinds` 도장 축**이 이 자리다.
3. CLAUDE.md 의 "기전 전체" 조항 위반. 지금은 어휘만 빠지고 기전은 돈다.

#### 🔴 진짜 긴장 — 두 세계가 같은 손잡이 하나를 공유한다

이게 이 항목의 핵심이고, 이전 판이 못 적은 것이다. **D-4 를 그냥 되돌리면(`Inf`) SMDP 가
깨진다.** `sojourn.jl` 이 zone 을 **경쟁 위험**으로 적분하기 때문이다:

```julia
if λz > 0.0
    dz = Ez / λz          # zone 은 상수율
    dz < Δ_fail && (Δ_fail = dz; who = :zone)
end
```

`mtbf_zone_s = Inf` 면 `λz = 0` 이고 zone 은 생성 시뮬레이터 `G(s,a)` 에서 **일어날 수 없는
사건**이 된다 — SMDP 에 zone 팔이 없어진다. D-4 가 존재하는 이유가 정확히 그것이다.

**즉 SMDP 세계는 `λz > 0` 을 요구하고, OOD 라벨 세계는 `λz = 0` 을 요구한다.
같은 상수 하나가 둘을 다 정하고 있다.** 결정은 "zone 을 켤 것인가"가 아니라
**"이 차이를 어디에 두고 어떻게 도장 찍을 것인가"** 다.

#### 선택지

| | 설계 | 대가 |
|---|---|---|
| **A** | `_hz_fire_zone!` 앞에 **에피소드 kind 게이팅**을 넣는다(`HazardParams` 에 `zone_enabled` 같은 필드 추가, known kind 면 false) | CLAUDE.md 조항과 정확히 일치. 대가: `hazard.jl` 이 "학습/테스트" 라는 데이터셋 개념을 알게 된다(계층 침범). 실행 레인엔 kind 개념이 없어 별도 규약 필요 |
| **B** | 라벨 레인에서 known kind 일 때만 `DS_MTBF_ZONE=Inf` | 손잡이 하나. `hazard.jl` 무손. 대가: **두 레인이 또 갈린다** — 이 레포가 이미 세 번 덴 그 모양(`DS_HOTSWAP` 등). 그리고 zone 레인에선 배경 zone 이 여전히 돌아 **주입 zone 과 배경 zone 이 섞인다** |
| **C** | 그대로 두고 **`train_kinds` 도장으로 기록만** 하고 오염률을 논문에 적는다 | 가장 정직하고 가장 싸다. 대가: OOD 주장이 "한 번도 안 봤다" → "1.9 % 봤다" 로 약해진다 |
| **D** | zone 을 **라벨 레인에서만 명시적 주입**으로 한정하고, SMDP 의 `λz` 는 **별도 파라미터**로 분리한다(두 세계를 이름부터 가른다) | 긴장을 구조적으로 푼다. 대가: 가장 큰 변경. `HazardParams` 가 갈라지고 도장 축도 하나 더 필요 |

**어느 쪽이든 `train_kinds` 도장 축은 필요하다** — A·B·D 는 "뺐다"를 증명해야 하고 C 는
"안 뺐다"를 기록해야 한다.

### 7-2. 실행 레인이 hot-swap 중 본체를 견인한다 (레인 정합성)

#### 배경 — `fire_clear` 와 hot-swap 이 서로 배타적인 이유

로봇이 고장나면 두 가지 복구가 가능하다:

- **Replace**: 창고의 예비 로봇이 와서 일을 넘겨받는다. 고장 본체는 쓸모없으므로 **견인해서
  치운다**(`fire_clear = true`). 안 치우면 씬에 장애물로 남는다.
- **hot-swap** (`:via_depot`): **정체성 보존** 교체다. 로봇 id 는 그대로 두고 **본체만** 창고에서
  갈아끼운다. 그래서 본체는 창고로 돌아가야 하고, **견인해서 없애면 안 된다.**

`tools/demos.jl:2912` 가 그 의도를 한 줄로 적어 뒀다:

> `# hot-swap 은 고장 본체를 창고로 되돌려 정체성을 보존하므로 견인(clear)하면 안 된다.`

#### 기전 — 세 레인이 이것을 어떻게 정하는가

| 레인 | 코드 | `fire_clear` | hot-swap |
|---|---|---|---|
| `tools/demos.jl:2913` | `fire_clear = !HOT_SWAP` | 유도됨 ✅ | 조건부 |
| `gen_oracle_dataset.jl:159` (라벨) | `fire_clear = !(DS_HOTSWAP == "1")` | 유도됨 ✅ | 조건부 |
| 🔴 `tools/monitor/run_demo.jl:629` (실행) | `CB.enable_hazard!(env; seed = HZ_SEED_USED)` — **`params=` 없음** | **`true`**(기본값) | `:644` 가 **ON** |

**독립적인 두 레인이 같은 규칙을 유도하는데 실행 레인만 안 한다.** 원인은 `params=` 누락이고,
`HazardParams()` 의 기본값 `fire_clear = true` 가 hot-swap 이 꺼져 있을 때만 옳기 때문이다.
그래서 실행 레인은 **hot-swap 하면서 동시에 본체를 견인**한다.

#### 무엇이 깨지는가

라벨은 "그 세계의 정답"일 뿐이다. 배포 물리와 라벨 물리가 다르면 정책은 **없는 세계의 최적**을
배운다. CLAUDE.md 가 이 실패를 이미 세 번 기록했다(`DS_HOTSWAP` 누락으로 fault 발화율
100 % → 23 %, `4b6b2d35` 의 라벨러/평가 불일치, `SwapBattery` 한 줄 누락으로 적중 0/6 ↔ 6/6).

#### 선택지 — 그리고 내 권고

증거가 한쪽으로 쏠려 있다: **실행 레인이 버그**다(두 레인이 독립적으로 반대를 유도하고,
`demos.jl` 주석이 이유를 적어 뒀다). 그래서 이건 "어느 쪽이 옳은가"보다 **"언제 고치는가"** 에

| | 설계 | 대가 |

### 7-3. N-G1 이 FAIL 했고, **원인의 98 % 가 관측창 설계**다

> ⚠️ **이 절은 전면 교체됐다.** 이전 판은 T9 의 숫자(`KS 0.1189` · `2.8배` · `80.7 %`)를
> 인용했는데, **T10 이 그 세 숫자를 명시적으로 폐기했다**(T10 보고서: "T9 의 세 숫자를 이
> 보고서의 어느 판정에도 쓰지 않았다"). 아래는 T10 의 실측이다.

#### 배경 — N-G1 이 무엇을 재는가

MCTS 는 **경량 레인**(`sample_sojourn`, `s` 만 보는 수학)으로 `τ` 를 샘플링한다. 그게 **엔진**
(무거운 레인, 실제 시뮬)과 같은 분포를 내야 트리가 진짜 세계를 탐색하는 것이다. N-G1 은 두
`τ` 표본을 **2표본 KS 검정**으로 비교한다.

#### 기전 — 무엇이 KS 를 만드는가 (T10 분해)

T10 이 두 후보 기전을 각각 껐다 켜서 몫을 쟀다. **같은 무거운 레인 위에서**(엔진 궤적은 한 벌)
돌렸으므로 칸 사이의 차이는 오직 경량 레인의 손잡이에서 온다.

| 기전 | 손잡이 | 적합/측정값 | KS 에서 제거한 양 | **몫** |
|---|---|---|---|---|
| D-6 rate boundary | `RHO[]` | **1.000** | 0.077635 → 0.077635 | **0 %** |
| `dur == 0` 드레인 | `DRAIN_DT[]` | 0.0 / 0.025 / 0.050 | 0.077635 → 0.077635 | **0 %** |
| 🔴 **미설명** | 없음 | — | 남은 **0.077635** | **100 %** |

**두 0 은 서로 다른 종류의 0 이라 뭉치면 안 된다:**

- **ρ 의 0** = "적합값이 이미 게이트가 돌던 값". 두 씬(150·200 정점)에서 **독립적으로 1.000**.
  ρ 를 1.5 로 밀면 KS 가 28.8 % 줄지만 그 바닥조차 `D_crit` 의 **2.33배**이고, 2.0 으로 더
  밀면 **오히려 나빠진다**. ⇒ **ρ 로는 어떤 값을 넣어도 게이트가 안 닫힌다.**
- **드레인의 0** = "효과가 작다"가 아니라 **"이 창에서 한 번도 발화하지 않는다"**.
  `n = 37612` 전수에서 `n_drain = 0`, 세 칸의 τ 벡터가 **비트 동일**. (8배 긴 창에서야 6표본당
  1회 뜨고, 그때도 표본당 0.004 s = 중앙값 τ 의 0.07 %.)

#### 🔴 그래서 남은 100 % 는 무엇인가 — **관측창 끝의 검열 원자**

out-of-sample 재검(`n = 37612`, 적합 ρ):

```
KS = 0.071121 · p = 3.67e-83 · D_crit 의 5.99배 · c_hat = 0.8783
그 KS 중 0.0697 (= 98.1 %) 이 관측창 검열 원자 하나다  (light 6161 vs heavy 3538)
```

**두 레인이 갈리는 자리는 분포의 몸통이 아니라 창의 끝이다.** 20 초 지평에서
경량은 **16.4 %**, 엔진은 **9.4 %** 가 검열된다 — 경량이 **너무 많이 살아남는다**.
그리고 이 항은 ρ 를 적합할수록 **커진다**(88.5 % → 98.1 %).

이건 두 가지로 읽힌다. **그 갈림이 이 항목의 결정이다:**
- (i) **진짜 λ 격차** — 경량의 누적위험이 엔진의 88 % (`c_hat = 0.8783`). 그러면 제3 기전을 쫓아야 한다.
- (ii) **창 설계 문제** — 20 초는 분포의 꼬리를 자르는 자리이고, KS 는 잘린 자리의 질량 차이를
  통계량으로 바꾼 것뿐이다. 그러면 고칠 것은 모델이 아니라 **게이트**다.

#### 🔴🔴 그리고 게이트 자신이 재현되지 않는다

T9(laneJ)와 T10 이 **같은 ρ · 같은 `n` · 같은 프로브 스텝 94 · 같은 `MODE_M`** 에서 잰 값:

| 레인 | KS |
|---|---|
| T9 (`laneJ`) | **0.1189** |
| T10 (`laneL`) | **0.0776** |

**1.53 배.** 표본 탓이 아니라 **디렉토리(= 컴파일 캐시 = 세계)** 탓이다 — §4 의 근본 원인이
**게이트의 판정 자체를 오염시키고 있다.** T9 이 본 "ρ 에 대한 KS 단조성"도 T10 레인에서는
**단조가 아니다.**

⇒ 🔴 **N-G1 을 다시 판정하기 전에 §4 의 입력 정준화(C8)가 먼저 와야 한다.** 안 그러면

#### 선택지

|---|---|---|

### 7-4. `engage_fallback!` 은 "복구 가능"이 아니라 **런의 영구 종료**다 (안전 의미론)

#### 배경 — 안전 폴백이 무엇을 하는가

LLM 이 낸 제안이 거부되면 안전 폴백으로 떨어진다. `engage_fallback!` 이 `RESPEC_HOLD[]` 를
켜고, `step_environment!`(`route_planning.jl:422`)가 **매 스텝** 그 플래그를 읽어 **모든 RVO
에이전트의 선호속도를 0 으로** 만든다. 속도 0 은 어떤 로봇도 금지구역으로 데려갈 수 없으므로
**언제나 사용 가능한 안전 행동**이다 — 그 논증은 옳다.

#### 기전 — 문서와 실제가 반대다

`engage_fallback!` 의 **자기 docstring**(`replan.jl:1750-1763`):

> The **recoverable** fallback action: hold all agents (line stop).
> …
> Callers that intend the build to CONTINUE past a fallback **must pair this with
> `release_fallback!`** — the flag is global and is never cleared on its own.

그런데 `release_fallback!` 자신의 docstring(`replan.jl:1771`):

> "Release the line-stop so the simulation resumes **(used by tests / resume paths)**."

**production 호출자는 0 개다.** `src/` 전체에서 `release_fallback!` 는 (1) export 줄,
(2) docstring·주석, (3) 정의 자신 — 이 셋으로만 나온다. 아무도 안 부른다.

⇒ **실제 의미론은 "첫 fallback = 런의 영구 종료"** 이고 문서는 그 반대를 말한다.

#### 🔴 그리고 이건 재발이다

`verifier.jl:281-285` 에 **똑같은 실패 모양이 2026-08-18 에 정정된 기록**이 있다:

> "(This docstring previously claimed the build keeps running, on the strength of an opt-in
> `set_failclosed_stop!` that no caller ever set; the claim was wrong about which mechanism
> carries the stop. Corrected 2026-08-18 …)"

**같은 파일 스무 줄 옆에서 같은 모양이 다시 나왔다** — "아무도 켜지 않는 opt-in 을 근거로
'빌드는 계속 돈다'고 주장하는 docstring". 한 번은 사고고 두 번은 패턴이다.

#### 무엇이 깨지는가 — SMDP 에서

이 태스크군의 안전 논증은 **"`verify()` 가 전이함수의 문이고, 거부는 NOOP 과 같은 전이"** 다
(§3-5). 그런데 거부 분기의 다수가 `engage_fallback!` 을 부른 **뒤** `:rejected` 를 돌려준다
(relocate · zone · replace · generic — `replan.jl:847-848`).

즉 **거부는 NOOP 과 같은 전이가 아니라 흡수 상태(absorbing state)로 가는 전이다.**
MCTS 가 그 자식 아래를 탐색하면 **전부 죽은 세계**다. `τ` 도 `R` 도 그 아래에서는 의미가 없다.

§5 의 결정 6("fallback 발동 시 **상태**를 보라, 전이를 보지 말라")이 이미 이 사실 위에 서 있다.

#### 선택지

| | 설계 | 대가 |
|---|---|---|
| **A** | **docstring 을 `terminal` 로 고친다.** 코드는 안 건드린다 | 가장 싸고 정직. 대가: SMDP 가 **흡수 상태를 명시적으로 갖게 된다** — 트리·버퍼·보상이 그것을 알아야 하고, 그게 모델 정의의 일부가 된다 |
| **B** | **정지가 스스로 만료되게 한다**(타이머 또는 "다음 결정 epoch 에서 해제") | line-stop 이 진짜로 회복 가능해진다. 대가: **동역학 변경 → generation bump → 재스윕**. 그리고 "얼마 뒤 해제"가 새 손잡이이고 그 값이 결과를 바꾼다 |
| **C** | **production 호출자를 넣는다** — 어디서 부를지를 정한다 | B 의 명시적 판. 대가: "어디서"가 곧 의미론 결정이고, 잘못 고르면 위험한 세계에서 라인을 다시 돌린다 |

**이게 왜 사용자 결정인가**: line-stop 이 **흡수 상태인가 회복 가능한 상태인가**는
버그가 아니라 **SMDP 의 정의**다. `τ` 와 `R` 의 값이 달라지고, "escalation" 이 무엇을 뜻하는지가
달라진다.

### 7-5. 기하적 불가능이 **fail-stalled** 다 (종료 조건)

#### 배경 — C4 가 무엇을 바꿨나

zone 이 빌드를 막으면 LLM 이 `TranslateBuild(Δ)` 로 빌드 전체를 옮기자고 제안한다.
C4 이전에는 **가드가 없어서**(fail-open) 잘못된 Δ 가 **조용히 집행**됐다 — 로봇이 구역
가장자리에 영원히 주차했다. C4 가 기하 검증기를 넣어 이제 **정상적으로 거부**된다.

#### 기전 — 거부는 옳은데, 거부 뒤에 갈 곳이 없다

`tools/e2e.jl mock_respec` 실측(C4 보고서):

```
[RESPEC] TranslateBuild Δ=(5.8896, 4.2194) REJECTED (residual_blocked):
         future work still intersects an active zone after Δ -> no mutation
closed 0 -> 145/289   status=stalled   FAIL
```

전이는 **있다**(거부는 정상 전이다). 예외도 안 난다. 그런데 **에피소드가 145/289 에서 그냥
정지하고 아무 일도 안 일어난다.** 다른 팔로 재시도하지도, 사람에게 넘기지도, "이 상태는
해결 불가"라고 선언하지도 않는다.

리뷰어의 표현이 정확하다:

> **"fail-open 이 fail-stalled 가 됐고, 둘 다 에피소드를 끝내지 않는다."**

#### 무엇이 깨지는가 — SMDP 에서

`G(s,a) → (s′, R, τ)` 에서 **`τ` 가 정의되지 않는다.** 에피소드가 지평까지 타면 그 행동의
비용이 "지평 전체"로 기록되는데, 그건 **그 행동의 비용이 아니라 에스컬레이션 부재의 비용**이다.
정책은 "이 행동은 끔찍하다"를 배우는데 사실은 "이 상황에 출구가 없다"이다.

그리고 D-10(**심의시간 = 0 으로 가정**)이 이미 이 자리를 건드린다 — CLAUDE.md 가
"escalation 률을 비용 대비 이득으로 읽지 말 것, 비용 항이 모델에 없다"고 적어 뒀다.

#### 선택지

| | 설계 | 대가 |
|---|---|---|
| **A** | **terminal-infeasible 로 선언하고 에피소드를 끝낸다**(고정 페널티 `R_stall`) | `τ` 가 유한해지고 SMDP 가 잘 정의된다. 대가: `R_stall` 이 새 손잡이고 그 값이 정책을 바꾼다 |
| **B** | **다른 팔로 재시도**(fallback 사다리: TranslateBuild 실패 → ForbidZone → …) | 가장 유용. 대가: 재시도가 결정 epoch 를 만드는가? 만들면 D-10 의 "심의시간 0" 가정이 더 세게 깨진다 |
| **C** | **사람 핸드오프 = 에피소드 종료 + 별도 라벨** | 실제 시스템의 정직한 모형. escalation 을 1급 결과로 만든다. 대가: 라벨 스키마 변경 |
| **D**(현재) | **측정만 하고 권고는 C5 가** | 결정을 미룬다. 대가: T14/C5 가 이 세계 위에서 예산을 쓴다 |

**지금 배정은 D 다**(C5 소유). 위 A~C 중 하나를 미리 정해 주면 C5 의 브리프가 훨씬 좁아진다.

### D-12 — N-G1 의 검열 항을 통계량에서 분리한다
