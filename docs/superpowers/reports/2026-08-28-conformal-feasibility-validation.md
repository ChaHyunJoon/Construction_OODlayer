## 1. 청구별 판정

### C1. §0 "R3 FAIL" — **CONFIRMED**

- **반증 관측:** 격상률이 α 에 따라 움직이면 반증.
- **내 재유도:** OOF(leave-one-instance-out) Ĵ, 절대잔차, 대칭구간, `gap ≤ 2q` 규칙으로
  α ∈ {0.05, 0.1, 0.3} 에서 **전부 9/12 = 0.750**. α 격자를 0.001~0.99 로 넓혀도 값은
  {1.000, 0.750, 0.667} 셋뿐이다.
- **격자 비의존 형태(내가 따로 확인):** `q` 는 33개 잔차의 순서통계량이므로 `k=1..33` 을 전수로
  훑었다 → `k=1` 에서만 8/12, `k=2..33` **전부** 9/12, `k>33`(q=∞) 이면 12/12. 즉
  α ∈ [1/34, 33/34] 의 **32/34 = 94.1%** 구간이 한 계단이다. 보고서 §3 의 주장과 정확히 같다.
- **음성 대조:** 같은 코드에 gap 을 1e9 로, 잔차를 1.0 으로 바꾼 합성 입력을 넣으니 격상률
  **0.000** 이 나왔다. 격상 계산은 0 을 낼 수 **있고**, 이 데이터에서 안 나온 것이다.

논증(메뉴 구조 → kind)은 옳지만, "kind 와 일치" 를 "kind 가 원인" 으로 읽으면 그 이상을 주장하는
것이다. §6 이 이 교락을 명시해야 한다.

### C7. §6 "`duplicate_pairs` n_pairs = 0, 쌍둥이 9쌍은 전부 같은 kind·같은 seed" — **부분 CONFIRMED, 함의는 REFUTED**

| 정의 | 내 재유도 | 판정 |
|---|---|---|
| `duplicate_pairs` 그대로 (kind 다름 + **모든** 공유팔 동일) | **0쌍** | 보고 CONFIRMED |
| 바이트 동일 공유팔 **≥2** 개 | **9쌍**, 전부 same kind·same seed | 보고 CONFIRMED |
| 바이트 동일 공유팔 **≥1** 개 | **18쌍, 그중 9쌍이 kind 간** | 🔴 보고에 없음 |

🔴 `fault_sN_sev1.0_sp3` 의 **macro 1(Replace) 행이 `battery_sN_sev{0.02,0.3,0.5}` 의 macro 1 행과
바이트 동일**하다(s1: `complete=True, closed=291, makespan=22.85, energy_J=96206.58221499549`;
s2·s3 도 같은 모양). 즉 **kind 간 누출은 실재한다** — 다만 공유팔 2개 중 1개에서만 일치해
`duplicate_pairs` 의 `len(shared)>=2 and all(...)` 문턱에 걸리지 않을 뿐이다.

보고는 `duplicate_pairs` 의 **`ka==kb` 맹점**은 정확히 짚었지만 **`all(shared)` 맹점**은 못 짚었고,
그 결과 "9쌍 전부 같은 kind" 라는 참인 문장이 "kind 간 누출은 없다" 라는 **거짓 함의**를 나른다.
브리프의 §6 지시를 정정한 것 자체는 옳으나(그 함수는 실제로 0을 낸다), **정정이 절반이다.**
LOIO 로 `fault_s1` 을 빼도 그 instance 의 개입 팔과 **바이트 동일한 학습행 3개**가 남는다.

### C8. §0 "잔차의 교환가능성 자체는 통과했다" — 🔴 **REFUTED**

- **이 청구가 참이려면:** R4 가 교환가능성을 실제로 시험하는 검사여야 한다. **반증 관측:**
  교환가능성이 심하게 깨진 잔차 배치를 넣어도 R4 가 PASS 를 내면, R4 PASS 는 교환가능성의
  증거가 아니다.
- **음성 대조 (핵심 실측).** 대상 도구를 `/tmp` 로 복사해 `measure()`/`coverage_leave_instance_out`
  을 그대로 부르되 잔차만 갈아 끼웠다. 무작위·적대적 잔차 배치 **4000회**(지수·로그정규·
  파레토·instance별 스케일 10⁻³~10⁶·instance 폭발):

  | α | R4 FAIL 횟수 | 최소 여유(coverage − need) |
  |---|---|---|
  | 0.05 | **0 / 4000** | +0.0091 |
  | 0.10 | 148 / 4000 | **−0.0015** (= 1행) |
  | 0.20 · 0.30 · 0.50 · 0.70 | **0 / 4000** | +0.0076 · +0.0167 · +0.0348 · +0.0530 |

  손으로 짠 최악 배치도 전부 PASS 다. 특히 **instance 별로 잔차를 1, 2⁸, 3⁸, …, 12⁸(≈4.3e8)로
  주는 완전 비교환 배치**의 coverage 는 `0.939 / 0.879 / 0.818 / 0.727 / 0.545 / 0.364`
  — **1−α 를 거의 그대로 따라간다.**
- **왜 그런가:** LIO 라도 calibration 은 33개 중 30~31개를 evaluation 과 **공유**한다. 그래서
  coverage 는 잔차 분포와 무관하게 `k/n ≈ 1−α` 에 고정된다. 여기에 `need = 1−α−0.05` 의
  0.05 슬랙(≈1.65행)이 남은 흔들림(최대 2행)을 흡수한다.
- **그리고 진짜로 재면 교환가능성은 깨져 있다.** calibration/evaluation 을 의미 있는 축으로
  가르면:

  | 대조 | α=0.05 | α=0.10 | α=0.30 | 목표 |
  |---|---|---|---|---|
  | macro{1,2} 로 교정 → **macro 0** 평가 | **0.000** | **0.000** | **0.000** | 0.95/0.90/0.70 |
  | 완주행으로 교정 → **미완주행** 평가 | **0.000** | **0.000** | **0.000** | 〃 |
  | battery 로 교정 → fault 평가 | 0.833 | 0.833 | 0.500 | 〃 |

  잔차는 27행(13.2~234.3, 중앙 87.3) / 6행(1059.2~7585.5, 중앙 3180.9)의 이봉이고, 그 분할선이
  정확히 `complete` 다. **조건부 coverage 0.000 은 "반증 못 했다" 가 아니라 "반증됐다" 이다.**
- **결론:** `coverage_holdout ≈ 1−α` 는 **LIO 구성이 자동으로 만들어 내는 산물**이다. 보고 §5 의
  "'교환가능성이 성립한다' 가 아니라 '33행으로는 반증하지 못했다'" 는 **여전히 너무 관대하다**
  (반증됐다). 그리고 §0 의 "교환가능성 자체는 통과했다" 는 **틀렸다.**

## 2. 적대적 다섯 질문

**Q1. 전량 적합 Ĵ 를 쓰면 결론이 바뀌는가 — 아니다(오히려 강해진다).**
전량 적합 잔차 `[26.476, 6362.984]`, gap battery `[2.817, 8.067]` / fault `[18470.7, 18475.7]`.
`k=1..33` 전수: **전부 9/12**. 즉 도달 가능한 격상률이 `{0.750, 1.000}` 둘로 줄어 OOF 보다 **더**
퇴화한다. R3 FAIL 은 OOF 선택의 산물이 아니다.

**Q2. 부호 잔차 + 비대칭 구간이면 바뀌는가 — 아니다.**
`[Ĵ+lo, Ĵ+hi]`, `lo`=α/2 하위·`hi`=1−α/2 상위 유한표본 분위수, 겹침 ⟺ `gap ≤ hi−lo`.
α=0.05 → `hi=∞`(k=34>33) → **12/12**; α=0.10 → width 11366.4 → 9/12; α=0.30 → width 247.5 → 9/12.
결론 동일(α=0.05 에서는 더 나쁘다).

**Q3. 행 단위로 세면 바뀌는가 — 아니다. 다만 보고가 분모를 명시하지 않았다.**
instance 단위 **9/12 = 0.750**, 행 단위 **27/33 = 0.818**. 둘 다 α 전 구간에서 상수이고 α 근처가
아니다. 라우팅 판정의 단위는 사건(instance)이므로 12 가 맞지만, **보고 어디에도 그 선택이 적혀
있지 않다.** 이 레포의 분모 이력을 생각하면 §2 표에 한 줄 필요하다.

**Q4. `coverage_holdout ≈ 1−α` 는 교환가능성의 증거인가 — 아니다, LIO 가 자동으로 만드는 산물이다.**
구분하는 대조와 그 결과는 C8 에 실측으로 있다. 요약: (a) 완전 비교환 잔차(instance별 8제곱
계단)도 coverage 가 1−α 를 따라간다, (b) 적대적 4000회 중 α=0.10 을 빼면 FAIL 0회, (c) 조건부
coverage 는 0.000. 셋 다 같은 방향을 가리킨다.

**Q5. gap 의 이봉성은 surrogate 의 성질인가, J 자신의 성질인가 — J 자신이다.**
**진짜 J** 의 top1−top2 gap 을 직접 쟀다:
`[0.00035, 0.0205, 0.253, 1.479, 2.695, 2.889, 2.900, 2.900, 109.5 | 17778.6, 18870.4, 24976.9]`.
빈 구간 `(109.5, 17778.6)` 이 surrogate 없이도 그대로 있다. 절벽은 `C_fail=10000` 이고,
fault 3개는 팔이 둘뿐이라 절벽이 **top-1 과 top-2 사이**에 놓인다(battery 는 완주 팔이 2개 이상이라
미완주 NOOP 이 3순위로 밀린다). 보고 §4-2 의 진단은 옳고, 이 측정이 그것을 surrogate 와 무관하게
확증한다.

## 3. 🔴 대상 보고 §6 이 빠뜨린 것 (추가돼야 할 한계)

1. **R4 는 이 표본 위에서 사실상 실패할 수 없는 검사다.** 적대적 4000회 실측(C8). **R4 PASS 를
   근거로 어떤 것도 세우면 안 된다.** — 이 레포가 이미 한 번 당한 실패 모양이다.
2. **조건부 coverage 는 0.000 이다**(macro 축·완주 축). 잔차는 실제로 교환가능하지 않고, 그
   비교환성의 축이 하필 **라우터가 조건부로 쓰는 축(팔)** 이다. §7-2 의 "Ĵ 를 한 자릿수 정확하게"
   만으로는 안 풀린다.
3. **kind 간 누출이 실재한다**(C7, 9쌍). §6 의 정정은 절반이다.
4. **격상률의 분모(instance 12 vs 행 33)가 명시돼 있지 않다.** 0.750 vs 0.818.
5. **퇴화 분기가 한 번도 발화하지 않았다.** 12 instance 전부 팔 ≥2 라 `no_arms`·`single_arm` 은
   시험되지 않았다. 축 2 규칙의 절반이 미측정이다(도구에는 구현돼 있고, 내가 합성 입력으로
   `single_arm` 분기가 발화함을 확인은 했다).
6. **`kind` 는 `n_arms` 및 runner-up 완주여부와 완전히 교락돼 있다**(C4).
7. **JSON 의 α=0.95 `R4: PASS` 는 부동소수 잔여물 위에 서 있다.** `1−0.95−0.05` 가 파이썬에서
   `4.163336342344337e-17 > 0` 이라 `VACUOUS` 규칙(`need <= 0`)을 **간발로 피한다.** 산술적으로는
   need = 0 이므로 그 칸은 VACUOUS 다. 보고 산문은 "문지방 ≈0" 으로 짚었지만 **기계가 읽는
   JSON 은 안 짚는다** — Task 3 이 JSON 을 재유도 대상으로 삼으므로 여기서 새면 조용히 샌다.

## 5. RISKS (아무도 안 물어본 것)

- 🔴 **`R4 = PASS` 라는 문자열이 12칸 중 8칸에 박힌 채 JSON 에 커밋돼 있다.** Task 3 이 이 JSON 을
  재유도 대상으로 삼는데, "PASS 8칸" 을 세는 소비처가 생기면 **실패할 수 없는 검사의 개수를 세는
  지표**가 발행된다. `R4` 값을 `NOT_INFORMATIVE` 로 바꾸든, 최소한 JSON 에
  `"r4_can_fail": false` 같은 필드를 같이 내야 한다.
- ⚠️ **α=0.90 의 `need = 0.049999999999999975`, α=0.95 의 `need = 4.163336342344337e-17`.**
  `need <= 0.0` 이라는 VACUOUS 판정 기준이 부동소수에 노출돼 있다. `need <= 1e-9` 로 두면 α=0.95 는
  올바르게 VACUOUS 가 된다. 지금은 float 잔여물이 판정을 가른다.
- ⚠️ **라벨셋의 팔 결과가 실행 단위로 공유되고 있다.** seed 당 macro1/macro2 결과가 severity 셋과
  fault instance 하나에 걸쳐 바이트 동일하다. 즉 33행의 **독립 시뮬레이션 실행은 33개가 아니다**
  — s1 만 봐도 macro1 결과는 4개 행(battery 3 + fault 1)이 **한 번의 실행**을 공유한다. 유효 표본은
  33보다 뚜렷이 작고, 이 사실은 `duplicate_pairs` 어느 정의로도 지금 보고되지 않는다.
  **모든 coverage·분위수의 유효 자유도가 과대평가돼 있다.**
- ⚠️ **`conformal_feasibility.py:91·134·149·167` 이 `[i for i, r in enumerate(rows) if ...]` 를
  instance 마다 다시 돈다** — O(n·instances). 33행에서는 무해하지만, 이 도구가 큰 라벨셋으로
  재사용되면 조용히 느려진다(정확성 문제는 없다).
- ⚠️ **`escalation()` 의 `esc = gap <= 2.0 * q` 는 `q = inf` 에서 True 를 낸다**(주석이 그렇게
  적는다). 의도된 것이지만, 그 True 는 *"겹친다"* 가 아니라 *"못 잰다"* 다. `escalation_rate_pooled`
  는 α ≤ 0.02 에서 **1.000 을 그대로 내보낸다** — `escalation_rate_honest` 는 None 으로 내리면서
  pooled 는 안 내린다. JSON 만 읽는 소비처는 "α=0.01 에서 100% 격상" 을 실측으로 읽을 수 있다.
- ⚠️ 이 검증은 `objective.json` `generation = 2026-08-21-reduced-state-sojourn-drainsigma0`,
  `objective_hash = 489268e6659e5ae9`, `vocab = v4-3arms` 위에서 이뤄졌다. 셋 중 하나라도
  바뀌면 위 숫자는 전부 무효다.
