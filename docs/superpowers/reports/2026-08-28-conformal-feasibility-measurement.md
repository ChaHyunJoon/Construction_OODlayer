## 0. 한 줄 판정

**R3 FAIL · R4 PASS(단, α 8칸에서만 측정됨 — 3칸은 측정불능, 1칸은 공허)** — 잔차의 교환가능성
자체는 통과했지만 **α 는 손잡이가 아니라 3칸짜리 계단이고 그 계단의 유일한 실측 가능 칸이 내는
격상 집합이 `kind` 분할과 정확히 일치**하므로, 오늘의 라벨셋 위에서 **축 2 를 지을 가치는 없다.**

## 1. 무엇을 어떻게 쟀나

추정기는 여섯 단계다.

1. **OOF 예측.** `LeaveOneGroupOut(groups=instance)` 로 12 폴드를 돌려 `SurrogateV2` 를 매 폴드
   재적합하고, held-out instance 의 행에만 `predict_J` 를 쓴다. 길이 33 의 `Ĵ` 를 얻는다.
   🔴 전량 적합 `Ĵ` 를 쓰지 않는 이유: 배포 레인이 마주치는 것은 **처음 보는 사건**이고,
   전량 적합 모델의 잔차는 자기가 외운 instance 의 잔차다.
2. **진실 J.** `objective.J_row` 하나에서만 온다. 재구현하지 않는다.
3. **잔차** `res = |Ĵ − J|`, 33 개.
4. **유한표본 분위수** `q = k 번째로 작은 잔차`, `k = ceil((n+1)(1−α))`. `k > n` 이면 `+inf` —
   *"q 가 크다"* 가 아니라 *"표본이 모자라 q 를 못 잰다"* 이고 둘은 다른 사실이다.
5. **격상 판정.** instance 마다 `Ĵ` 를 **직접 정렬**해 top-1/top-2 를 잡고 `gap = Ĵ₂ − Ĵ₁`,
   `gap ≤ 2q` 면 격상. (`surrogate_rank` 의 1순위도, `predict_delta_J` 도 쓰지 않는다 — 설계서 §3
   의 두 경고.)
6. **정직한 coverage.** instance `i` 를 뺀 잔차로 `q_i` 를 만들어 `i` 의 행이 `res ≤ q_i` 인지
   센다. 🔴 `q` 를 뽑은 그 표본으로 coverage 를 재면 정의상 `1−α` 라 순환논법이다.

**`escalation_rate_honest` 는 5번을 `q` 대신 `q_i` 로 다시 한 것**이고, 이 라벨셋에서는 pooled 판과
같은 값을 냈다(표 참조).

🔴 **`R4` 는 네 값을 가진다.** `PASS`/`FAIL` 말고도:
- `UNMEASURABLE` — 어떤 `q_i` 가 `+inf` 였다. 그러면 그 instance 의 행은 자동으로 "덮였다" 가 되어
  coverage 가 트리비얼하게 1.0 으로 올라간다. **측정 불능이 PASS 로 위장하는 자리**라 도구가 이
  경우 `coverage_holdout`/`escalation_rate_honest` 를 `null` 로 내리고 `honest_unmeasurable` 를 세운다.
- `VACUOUS` — `1−α−0.05 ≤ 0` 이라 문지방이 아무것도 주장하지 않는다.

넘어 12개 instance **전부** `q_i = +inf` 가 된다. `q_pooled` 가 α=0.03 에서 유한한 것(7585.451)과는
별개의 사실이다 — pooled 는 33 개 전부를 쓰고 per-instance 는 30~31 개만 쓴다.

⚠️ α=0.90·0.95 의 PASS 는 도구의 `VACUOUS` 규칙(`need ≤ 0`)에는 안 걸리지만 문지방이 각각 0.05 와
≈0 이라 **실질적으로 거의 아무것도 주장하지 않는다.** 실제로 내용이 있는 PASS 는 α ∈ {0.05, 0.1,
0.2, 0.3, 0.5, 0.7} 여섯 칸이다.

```
1.445 → 1.446   ×1.000
1.446 → 1.663   ×1.150
1.663 → 2.727   ×1.640

```

**2q 의 도달 범위와 겹쳐 본다.**
- α 격자 전체에서 유한한 2q: **[26.353, 15170.903]** (α ≤ 0.02 는 ∞).
- 그중 **측정 가능하고 공허하지 않은** 행(α ∈ [0.05, 0.95])만 보면: **[44.382, 15170.903]** — 342 배 범위.

이 342 배 구간이 빈 구간 `(30.963, 17304.157)` **안에 통째로 들어간다.** 즉 α 를 0.05 에서 0.95 로
19 배 움직여 2q 를 342 배 줄여도 **gap 을 단 하나도 건너지 않는다.** 🔴 **α 는 손잡이가 아니라 계단이다.**

**격자에 의존하지 않는 형태로 다시 쓴다.** `q` 는 33 개 잔차의 순서통계량이므로 도달 가능한 값은
그 33 개뿐이다. `k = 1..33` 을 전부 훑어 격상 개수를 세면:

| q 가 놓이는 곳 | α 구간 | 2q | 격상 |
|---|---|---|---|
| `k > 33` → ∞ | α < 1/34 ≈ 0.0294 | ∞ | **12/12** (측정불능 영역) |
| `k = 2..33` | 1/34 ≤ α < 33/34 ≈ 0.9706 | 44.382 … 15170.903 | **9/12** ← 격자 32칸 전부 |
| `k = 1` (최소 잔차 13.176) | α ≥ 33/34 | 26.353 | **8/12** (공허 영역) |

**α ∈ (0,1) 전체에서 격상률이 취하는 값은 {1.000, 0.750, 0.667} 셋뿐이고, 가운데 계단 하나가
α 구간의 94.1% 를 덮는다.** 그리고 그 계단만이 측정 가능하고 공허하지 않다. 격상률이 0.750 아닌
값을 가지려면 α < 0.0294 (거기선 coverage 를 못 잰다) 또는 α > 0.9706 (거기선 R4 문지방이 음수다)
여야 한다.

바닥이 왜 26.353 인가: **`q` 의 하한은 최소 잔차 13.176 이다.** 그런데 battery instance 9개 중
8개의 gap 이 2.841 이하다. 어떤 α 를 골라도 `2q ≥ 26.353 > 2.841` 이므로 **그 8개는 원리적으로
"확신" 판정을 받을 수 없다.** 이것은 격자가 성긴 탓이 아니라 잔차 분포가 gap 보다 두 자릿수 큰 탓이다.

## 4. R3 판정 — **FAIL**

설계서 §7 R3 은 *"known 사건의 escalation률이 α 근처인가"* 이고, 반증 관측을
*"0 이면 구간이 너무 넓어 축 2 가 아무것도 안 하는 것"* 으로 적었다(spec §8-1 항목 5 는 반대쪽도
같이 적는다 — *"높으면 conformal 미교정"*).

**실측은 두 반증 모양 중 어느 쪽도 아니고, 더 나쁜 세 번째다: 격상률이 α 에 대해 상수다.**

- α = 0.05 에서 격상률 0.750 (기대 0.05). α = 0.5 에서도 0.750. α = 0.95 에서도 0.750.
- 측정 가능하고 공허하지 않은 8 칸 **전부**에서 pooled 도 정직판도 0.750 이다.
- 그리고 §3 이 보였듯 이것은 격자 아티팩트가 아니라 α ∈ [1/34, 33/34] 전체의 성질이다.

α=0.7 근처에서 0.750 이 α 와 가까워 보이는 것은 **교정이 아니라 계단이 그 자리를 지나는 것**이다.
좌우 어느 쪽으로 α 를 움직여도 값이 안 따라온다.

세 결론 중 어느 것인가 — **"축 2 가 α 라는 손잡이를 제공하지 않는다"** 이다. 구간이 너무 넓어
아무것도 안 하는 것(격상률 0)도 아니고, 미교정이지만 움직이기는 하는 것도 아니다. **손잡이 자체가
없다.**

### 4-1. 🔴 격상 집합이 `kind` 분할과 정확히 일치한다 — 설계 전체에 대한 반증 후보

`escalated_instances` 를 `per_instance_kind` 로 교차분류했다.

| α | 격상된 instance | 격상 안 된 instance |
|---|---|---|
| 0.01, 0.02 | battery 9 + fault 3 = **12** | (없음) — 단, **측정불능** |
| **0.03 ~ 0.95** | **battery 9, fault 0** | **fault 3, battery 0** |
| 0.99 | battery 8 | battery 1 + fault 3 — 단, **공허** |

🔴 **측정 가능한 α 전 구간에서 격상 집합 = `{kind == battery}`, 비격상 집합 = `{kind == fault}` 로
정확히, 예외 없이 일치한다.**

설계서 §1 의 논증은 *"kind 색인은 경계를 얼린다 — known 집합이 `{fault, battery}` 라는 리터럴이면
surrogate 가 무엇을 학습하든 그 집합은 안 바뀐다"* 였다. **축 2 는 kind 를 입력으로 받지 않는데도
kind 와 동일한 분할을 낸다.** kind 를 안 쓰고 kind 를 재현한 것이고, 그렇다면 **얼어붙은 경계에서
아무것도 탈출하지 못했다.**

기전은 §5-1 에서 다시 쓰지만 한 줄로: **팔 메뉴가 이미 kind 색인이다.**
`action_registry.json` 이 `SwapBattery` 에 `"kinds": ["battery"]` 를 박아 두어 battery instance 는
3팔, fault instance 는 2팔이다. fault 는 팔이 둘뿐이라 **미완주 NOOP 이 필연적으로 runner-up 이
되고**, battery 는 완주하는 세 번째 팔이 있어 NOOP 이 3순위로 밀린다. gap 이 두 자릿수 갈리는
원인이 그 메뉴 구조이고, 그 메뉴 구조가 곧 kind 다.

⚠️ 정직하게 덧붙인다: n = 12 instance / 2 kind 이므로 "kind 와 일치" 는 **2분할이 우연히 맞을
확률이 낮지 않은 규모**다. 그러나 그것이 우연이 아니라 레지스트리의 `kinds` 필드에서 **결정론적으로**
따라 나온다는 것이 위 기전이다. 우연의 일치가 아니라 구조적 일치다.

### 4-2. 큰 gap 은 완주 절벽에서 온다 — J 가 이봉분포다

큰 gap 3개(fault instance)의 top-2 팔을 직접 봤다:

| instance | rank0 | rank1 (runner-up) | gap |
|---|---|---|---|
| fault_s1_sev1.0_sp3 | macro 1 Replace, `complete=true`, Ĵ=110.4 | **macro 0 NOOP, `complete=false`**, Ĵ=17414.5, closed 163/313 | 17304.2 |
| fault_s2_sev1.0_sp3 | macro 1 Replace, `complete=true`, Ĵ=116.5 | **macro 0 NOOP, `complete=false`**, Ĵ=20059.2, closed 223/313 | 19942.7 |
| fault_s3_sev1.0_sp3 | macro 1 Replace, `complete=true`, Ĵ=169.9 | **macro 0 NOOP, `complete=false`**, Ĵ=20059.2, closed 235/313 | 19889.3 |

**세 개 전부 runner-up 이 `complete == false` 다.** `objective.json` 의
`J = C_fail + C_unclosed·(total − closed) + tie_eps·makespan` (`C_fail = 10000`,
`C_unclosed = 100`) 이므로 진실 J 는 각각 25000 / 19000 / 17800 이다. **gap ≈ `C_fail` 절벽 그 자체다.**

귀결: **J 는 설계상 이봉분포다.** 완주 봉우리는 J ∈ [18, 130], 실패 봉우리는 J ∈ [17800, 25000].
- 봉우리 **사이** 간격 ≈ 17000~20000 — 어떤 α 로도 못 좁힌다(최대 2q = 15170.9).
- 봉우리 **안** 간격 ≈ 1.4~31 — 어떤 α 로도 못 넓힌다(최소 2q = 26.4).
- 그리고 잔차 자체가 두 봉우리에 걸쳐 있어(최소 13.2, 최대 7585.5) `q` 는 **두 봉우리의 혼합**에서
  뽑힌다. 즉 conformal 이 재는 "불확실성" 은 사실상 *"이 팔이 완주하는가"* 의 불확실성이고,
  **어느 봉우리 안에서도 해상도를 내지 못한다.**

conformal 이 여기서 하는 일은 **"완주/미완주를 가르는 이진 분류기"** 와 같다. 그것은 α 없이도
`complete` 필드 하나로 되는 일이다.

## 5. R4 판정 — **PASS(제한적)**

`coverage_holdout` 대 `1 − α − 0.05` 를 여덟 칸에서 실측했다. **FAIL 은 한 칸도 없다.**

| α | coverage | 필요 | 여유 |
|---|---|---|---|
| 0.05 | 0.970 | 0.900 | +0.070 |
| 0.10 | 0.909 | 0.850 | +0.059 |
| 0.20 | 0.818 | 0.750 | +0.068 |
| 0.30 | 0.727 | 0.650 | +0.077 |
| 0.50 | 0.485 | 0.450 | +0.035 |
| 0.70 | 0.333 | 0.250 | +0.083 |
| 0.90 | 0.121 | 0.050 | +0.071 (문지방 자체가 0.05) |
| 0.95 | 0.061 | ≈0.000 | +0.061 (문지방 자체가 ≈0) |

**측정하지 못한 칸:** α ∈ {0.01, 0.02, 0.03} — `n_q_infinite = 12`, 즉 12개 instance **전부** 의
`q_i` 가 `+inf` 라 coverage 를 재는 것이 불가능했다. 🔴 **이 세 칸을 "PASS" 로도 "FAIL" 로도 읽으면
안 된다.** 도구 수정 이전이었다면 이 자리가 `coverage=1.000, R4=PASS` 로 찍혔을 것이다 — 모든 잔차가
`+inf` 이하이므로.

**공허한 칸:** α = 0.99 — `1 − α − 0.05 = −0.04` 이라 문지방이 어떤 coverage 든 통과시킨다.

**해석의 폭.** coverage 의 분해능은 1/33 = 0.0303 이다. α=0.5 의 여유 +0.035 는 **행 1.2개**에
불과하다. 나머지 칸의 여유도 2~3행 규모다. **"교환가능성이 성립한다" 가 아니라 "33 행으로는
반증하지 못했다" 가 정확한 서술이다.** 0.05 의 슬랙이 문지방에 이미 들어가 있는 것도 감안해야 한다.

그리고 R4 PASS 는 R3 FAIL 을 구제하지 못한다. **잔차가 교환가능해도 gap 분포가 잔차 규모의 아래에
통째로 깔려 있으면 구간 겹침 판정은 상수다** — 이 라벨셋이 정확히 그 경우다.

## 6. 🔴 이 측정이 못 말하는 것

- **n = 12 instance / 2 kind / 33 행이다.** 어떤 결론도 이 표본 크기를 넘지 못한다. 특히
  §4-1 의 "kind 와 정확히 일치" 는 2분할 위의 관측이므로 **더 많은 kind 로 재확인해야 한다**
  (오늘의 라벨셋에는 `zone` 이 없다 — `train_kinds = battery,fault`).
- 🔴 **`q_i` 는 자기가 판정하는 instance 로부터 완전히 독립이 아니다.** `q_i` 를 만드는 "다른
  instance 의 잔차" 들은 각각 **자기 instance 를 뺀 OOF 모델**이 낸 것인데, **그 모델들은 instance
  `i` 를 학습에 포함했다.** 즉 `res[j]` (j≠i) 는 `i` 를 본 모델의 산물이다. 이것을 없애려면
  **중첩 LOIO**(바깥 폴드로 `i` 를 빼고, 안쪽에서 다시 LOIO 를 돌려 calibration 잔차를 만드는 것)가
  필요하고, n=33 에서는 안쪽 폴드가 더 작아져 `q_i = +inf` 영역이 넓어진다. **편향의 방향도
  불분명하다** — 유출은 잔차를 낙관적으로(작게) 만들어 `q` 를 줄이고 coverage 를 낮출 수도,
  잔차 분포를 좁혀 coverage 를 높일 수도 있다. **§5 의 coverage 숫자를 깨끗한 것으로 읽지 말 것.**
- 🔴 **LOIO 는 낙관적이다 — 그리고 그 이유를 실측으로 정정한다.** 이 태스크의 브리프는
  `eval_surrogate_v2.duplicate_pairs` 의 **kind 간** 쌍둥이 누출을 근거로 들었는데, 그 함수를 이
  라벨셋에 직접 돌린 결과는 **`n_pairs = 0` 이다**(docstring 의 "5쌍" 은 다른 세대의 라벨셋에 대한
  기록이다). 그러나 누출은 실재하고 형태가 다르다: **공유 팔 2개 이상이 바이트 동일한 instance 쌍이
  9쌍 있고, 9쌍 전부 같은 kind·같은 seed 다**(`battery_s{1,2,3}_sev{0.02,0.3,0.5}` 의 seed 내 3쌍씩).
  `duplicate_pairs` 는 `ka == kb` 면 건너뛰므로 **구조적으로 이 9쌍을 볼 수 없다.**
  귀결은 브리프의 취지보다 강하다 — LOIO 로 instance 하나를 빼도 **같은 seed 의 쌍둥이 둘이
  학습셋에 남는다.**
- **이 측정은 오늘의 surrogate(`SurrogateV2`)와 오늘의 라벨셋에 대한 것이다.** 둘 중 하나가 바뀌면
  다시 재야 한다. 특히 §4-2 의 결론(J 이봉성)은 `objective.json` 의 `C_fail = 10000` 에 직접
  의존하므로, 그 스칼라나 `generation` 이 바뀌면 이 보고의 gap 분포는 전부 무효다.
- **이 측정은 라우터가 아니다.** 아무것도 격상시키지 않았고, 실제 서비스 레인(`dspy_service.py` 의
  `support` 필터, `select_lane`)은 전혀 타지 않았다. 축 1(`vocabulary_gap`)에 대해서는
  **아무 말도 하지 않는다** — 설계서 §2-2 대로 오늘 support = 어휘 전체라 축 1 은 여전히 발화 영역이
  빈 상태다.
- **R5(두 축이 서로 다른 것을 잡는가)는 재지 않았다.** 축 1 이 한 번도 발화하지 않으므로 겹침 비율을
  정의할 수 없다.

## 7. 그래서 다음은 무엇인가

### 7-1. 오늘의 라벨셋 위에서 V2(축 2)를 짓지 않는다

근거는 §2·§3·§4 의 세 사실이고, 셋 다 α 격자에 의존하지 않는다.

1. **손잡이가 없다.** α ∈ (0,1) 전체에서 격상률은 {1.000, 0.750, 0.667} 세 값뿐이고, 그중 측정
   가능하고 공허하지 않은 것은 **0.750 하나**다. 손잡이 α 하나로 위험 예산을 조절한다는 설계서 §3 의
   약속이 이 라벨셋에서는 실현되지 않는다.
2. **경계를 못 옮긴다.** 그 유일한 계단이 내는 분할이 `{battery} / {fault}` 로 kind 분할과 정확히
   일치한다. 설계서 §1 이 kind 색인을 버린 이유가 *"경계가 얼어붙는다"* 였는데, 축 2 는 kind 를
   안 보고 같은 경계를 다시 그린다. **설계의 존재 이유를 축 2 가 충족하지 못한다.**
3. **기전이 밝혀졌다.** J 가 완주 절벽(`C_fail = 10000`) 때문에 이봉분포라, conformal 이 재는
   불확실성은 사실상 `complete` 이진값이다. 봉우리 **안**(gap 1.4~31)은 잔차 하한 13.2 때문에
   원리적으로 해상 불가능하고, 봉우리 **사이**(gap 17000~20000)는 최대 2q 15171 로도 못 덮는다.

⚠️ 이것은 *"conformal 이 원리적으로 틀렸다"* 가 아니다. **"오늘의 J 스케일·오늘의 잔차 규모 위에서는
축 2 가 정보를 하나도 더하지 않는다"** 이다. 축 2 를 그대로 배선하면 `escalate ⟺ kind == battery`
라는 상수 규칙에 α 라는 안 움직이는 손잡이를 붙인 것이 된다 — 오늘 걷어내려는 novelty 라우터보다
나을 것이 없다.

### 7-2. 축 2 가 되살아나려면 무엇이 참이어야 하는가 (V3 에 대한 요구)

이 측정은 **축 2 를 부활시킬 조건을 정확히 준다.** 셋 다 필요하다.

1. **J 의 이봉성을 걷어내거나, conformal 을 봉우리 **안**에서만 돌려야 한다.** 완주/미완주는 `complete`
   필드로 공짜로 갈린다 — 그 분기를 먼저 태우고 **완주 팔들끼리만** 잔차 분위수를 만들면 `q` 의 상단을
   혼자 끌어올리는 실패-분기 잔차(1059.2~7585.5, 6행)가 빠진다. 실측: 완주 27행의 잔차는
   13.2~234.3(중앙 87.3), 미완주 6행은 1059.2~7585.5(중앙 3180.9)다.
   ⚠️ 다만 이것만으로는 §4-1 이 안 풀린다 — **완주 팔이 2개 이상인 instance 는 battery 9개뿐이고
   fault 3개는 완주 팔이 1개라 `single_arm`(정보 부재)로 격상된다.** 분할이 뒤집히는 게 아니라
   여전히 kind 와 정렬된다.
2. **잔차 규모 < gap 규모가 성립해야 한다.** 실측: 완주 팔들끼리의 gap 은 9개 instance 에서
   1.445~30.963(중앙 **2.782**)인데 완주 행 잔차의 중앙값은 **87.3** 이다. **비가 31.4 배로 틀렸다.**
   `Ĵ` 가 지금보다 최소 한 자릿수 정확해지지 않으면 어떤 α 도 봉우리 안을 가르지 못한다. V3 는 축 2 를
   짓기 전에 **"완주 팔들 사이 잔차의 중앙값 < 완주 팔들 사이 gap 의 중앙값"** 을 게이트로 걸어야 한다.
3. **kind 가 팔 메뉴를 결정하지 않는 라벨셋이 있어야 한다.** `action_registry.json` 의
   `"kinds": ["battery"]` 가 살아 있는 한, 어떤 팔-기반 판정도 kind 분할을 물려받는다. 설계서 §5 의
   `train_macros` 도장은 이 문제를 못 푼다 — 메뉴를 좁히는 것은 학습셋이 아니라 레지스트리다.
   🔴 **설계서 §1 의 "kind 색인을 벗어난다" 는 주장이 유지되려면 레지스트리의 `kinds` 필드부터
   손대야 한다.** 이 보고가 밝힌 가장 하중 큰 사실이다.

### 7-3. 지금 당장 할 수 있는 것

- **축 1(`vocabulary_gap`)은 이 보고와 무관하게 살아 있다.** 설계서 §2-2 가 요구한 음성 대조(지원집합에서
  매크로 하나를 빼고 발화시키기)는 이 측정이 부정하지 않는다. 축 2 를 보류하고 축 1 만 먼저 짓는
  경로가 **설계서 §6 의 순서(4 → 5)와 이미 일치한다.**
- **재측정 트리거를 명시해 둔다.** 이 보고는 (a) `objective.json` 의 `C_fail`/`generation`,
  (b) `SurrogateV2` 의 구조, (c) `oracle_dataset.jsonl` 의 행 집합 — 셋 중 하나라도 바뀌면 무효다.
  CLI 한 줄이라 재측정 비용은 3.5 초다.
- **`zone` kind 를 포함한 라벨셋이 생기면 §4-1 을 다시 잰다.** 3 kind 위에서도 격상 집합이 kind
  분할과 일치하면 반증 후보가 반증으로 굳는다. 일치하지 않으면 §4-1 은 2분할 위의 우연으로 강등되고,
  그때는 §7-2 의 조건 1·2 만 남는다.
