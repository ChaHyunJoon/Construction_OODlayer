# 라이브 세션 런 토큰 + 구역 확정 전 무기록 설계

**한 줄:** 대시보드가 "지금 화면의 프레임이 내가 시작한 런의 것인지" 판별할 수단이 없어서 옛 녹화를
라이브인 양 보여준다. 런마다 토큰을 발급해 그 판별을 가능하게 하고, 존 런은 조작자가 구역을 확정하기
전에는 스트림 파일을 아예 열지 않는다.

## 1. 증상 (2026-08-12 실측)

조작자가 ③ Forbid Zone 케이스에서 `Start live session` 을 누르면, **구역을 그리기도 전에** OOD 이벤트
피드에 이미 구역이 주입됐다는 문장이 뜬다:

```
A no-go exclusion zone has appeared at (1.09, 0.42) with radius 0.07.
```

## 2. 근본 원인

### 원인 A — 폴링이 옛 녹화를 라이브로 오인한다 (관측된 증상의 원인)

`dashboard.html:1526` 은 폴링 대상을 접미사 없는 이름으로 정하고(`streams/tractor__zone.jsonl`),
`:1553-1558` 은 **그 파일이 비어 있지 않으면 즉시** 로드한다. 그런데 엔진은 env 빌드(3~4분)를 마치고
`render_demo.jl:755` 의 `CB.monitor_enable!` 에 도달해야 그 파일을 0바이트로 자른다. 그 사이 파일에는
**이전 녹화가 그대로 남아 있다.**

그 이전 녹화는 비대화형 렌더가 만든 것이므로 구역이 **자동 주입기**(`inject_blocking_zone!`) 산출물이다.
서명이 정확히 일치한다 — id `zone_blk_1`, 문구 "has appeared"(사람이 넣으면 "A human operator
injected"), 반지름 `DEMO_ZONE_R`(0.5) × 로봇 반지름 = 0.07. 복구한 Task 6 녹화본의 frame 0 이 위 문장
그대로였다.

**이것은 존 케이스만의 문제가 아니다.** 폴링 조건이 "비었나" 하나뿐이므로 battery·fault 를 포함한
**모든 라이브 케이스**가 env 빌드 동안 옛 녹화를 라이브인 양 보여준다.

### 원인 B — 확정 전에 녹화본이 파괴된다

`monitor_enable!`(`render_demo.jl:755`)은 pre_sim_hook 맨 앞, 즉 REQUIRE_ZONE 게이트(`:937`)보다 **먼저**
돈다. 그래서 조작자가 구역을 확정하기 전에 스트림 파일이 잘리고, 취소하면 옛 녹화는 이미 사라진 뒤다.
2026-08-12 세션에서 실제로 `tractor__zone.jsonl` 이 이렇게 덮였고 백업에서 되돌렸다.

### 원인 C — 평면도보다 먼저 도착한 zone 명령 (미해명)

문제의 zone 명령은 `requested_at = 20:45:58.014`, 즉 렌더 자식이 뜬 **14 ms 뒤**에 기록됐다. 평면도는
env 빌드가 끝나야 나오므로 조작자가 그것을 보고 고른 좌표일 수 없다. `postZone` 호출부는 사람 클릭
두 곳(`zoneGo`, `zoneConfirm`)뿐이고, `zoneConfirm` 이 런을 시작한 버전은 git 이력에 없다. 서버가 정적
파일에 캐시 헤더를 주지 않아 브라우저가 옛 UI 를 쓸 수는 있으나, 그것으로도 설명되지 않는다.

**원인을 특정하지 못했으므로 원인 대신 조건을 막는다** — §4-D 참조.

### 오해였던 것 (기록)

"명령 파일이 런 사이에 안 비워진다"고 한 번 판단했으나 **틀렸다.** `server.jl:85` 가 매 런마다
`open(cmdfile, "w")` 로 비운다.

## 3. 목표 / 비목표

**목표**
- 화면에 보이는 프레임은 조작자가 시작한 바로 그 런의 것임을 구조적으로 보장한다.
- 존 런은 조작자가 구역을 확정해야만 기록이 시작된다. 확정 전에는 기존 녹화본을 건드리지 않는다.
- 확정 없이 끝난 런은 산출물을 남기지 않는다.

**비목표**
- 자동 주입기(`inject_blocking_zone!` / `inject_staging_zone!`)는 **한 글자도 고치지 않는다.** 비대화형
  녹화와 오라클 격자가 그 함수들의 세계이고, 2026-08-12 D=20 산출물의 재현성이 거기 걸려 있다.
- 행동 어휘(`action_registry.json`)·정책·기준 정책을 건드리지 않는다.
- 원인 C 의 진짜 출처를 규명하는 것(브라우저 상태라 저장소 밖이다). 조건만 막는다.

## 4. 설계

### A. 런 토큰

`POST /run` 이 `run_id`(예: `time_ns()` 문자열)를 발급한다.

- 응답 본문을 JSON 으로 바꿔 `{"status":"started","run_id":...}` 를 싣는다. 기존 `"busy — …"` /
  `"already running"` 텍스트 응답은 대시보드가 문자열로 판별하므로(`dashboard.html:1541`) **그 형태를
  유지**한다.
- 자식에게 `MONITOR_RUN_ID` 환경변수로 넘긴다.
- 서버는 활성 런의 `run_id` 를 `/status` 에 함께 싣는다.

### B. 기록 시점을 게이트 뒤로

`render_demo.jl` 의 `CB.monitor_enable!(stream_path)` 를 pre_sim_hook 맨 앞에서 **게이트 통과 직후**로
옮긴다. 게이트가 없는 런(비대화형·비존 라이브)은 지금과 같은 자리에서 켠다 — 동작 변화 없음.

스트림을 연 직후 **첫 프레임보다 먼저** 한 줄짜리 헤더 레코드를 쓴다:

```json
{"run_id":"...","case":"zone","requires_zone":true,"started_at":<epoch>,
 "zone":{"x":0.5,"y":0.4,"r":0.3,"id":"..."}}
```

`zone` 은 조작자가 확정한 구역이며, 게이트가 있는 런에서만 존재한다.

이 헤더는 **스트림의 첫 줄이며 프레임이 아니다.** 프레임 소비자(`parseJSONL` 이후 재생 경로)는
`run_id` 키를 가진 레코드를 프레임 목록에서 제외한다. 게이트가 없는 런도 같은 헤더를 쓴다 — §4-C 의
판정이 모든 라이브 케이스에서 성립해야 하기 때문이다.

### C. 대시보드는 run_id 가 맞는 프레임만 받는다

`requestGeneration` 이 응답에서 받은 `run_id` 를 보관하고, 폴링은 "비었나" 대신 **"헤더 레코드가
있고 그 `run_id` 가 내 것인가"** 로 판정한다. 불일치·부재면 아무것도 로드하지 않고 준비 화면을
유지한다. 이 한 가지가 원인 A 를 모든 케이스에서 닫는다.

### D. 평면도 이전의 zone 주입은 거절한다

`POST /inject/zone` 은 활성 런의 `layout.json` 이 아직 없으면 **409** 를 돌려주고 명령 파일에 쓰지
않는다. 조작자는 평면도를 보기 전에 구역을 고를 수 없으므로, 그 전에 도착한 주입은 정의상 사람이
고른 것이 아니다. 원인 C 의 출처와 무관하게 조건이 막힌다.

응답 본문은 왜 거절됐는지 말한다: `"floor plan not published yet — draw the zone after it appears"`.

### E. 대시보드에 캐시 금지 헤더

정적 파일 응답 중 `dashboard.html` 에 `Cache-Control: no-store` 를 붙인다. UI 를 고쳐도 브라우저가 옛
파일을 쓰면 소용이 없다.

## 5. 데이터 흐름

```
[UI] Start live session
      → POST /run                     → run_id 발급, layout.json 삭제, 명령 파일 truncate, 자식 spawn
      ← {"status":"started","run_id":R}
[UI] run_id=R 보관, 스트림 폴링 시작(헤더 없으면 계속 대기), GET /layout 폴링
[엔진] env 빌드 … pre_sim_hook
      → dump_layout()                 → commands/<key>.layout.json
      → REQUIRE_ZONE 게이트에서 대기   ← 이 시점까지 스트림 파일은 손대지 않는다
[UI] 평면도 도착 → 조작자가 그림 → Confirm zone & start → POST /inject/zone
[서버] layout.json 존재 확인(없으면 409) → 명령 파일에 append
[엔진] 게이트 통과 → monitor_enable! → 헤더 레코드(run_id=R, zone=…) → 첫 스텝
[UI] 헤더의 run_id == R  → 그때부터 프레임 재생
```

취소 경로: `POST /abort` → 엔진이 `exit(0)`. 스트림을 연 적이 없으므로 **기존 녹화본이 그대로 남는다.**

## 6. 오류 처리

| 상황 | 동작 |
|---|---|
| 평면도 이전 `/inject/zone` | 409 + 사유. 명령 파일 미기록 |
| `run_id` 불일치 프레임 | 대시보드가 무시, 준비 화면 유지 |
| 헤더 레코드가 끝내 안 옴 | 기존 `/status` 폴링이 실패/완료를 잡아 기존 오류 배지 경로로 |
| 게이트 중 abort | 산출물 없음. 옛 녹화본 보존 |
| 옛 스트림에 헤더가 없음 | `Load previous recording` 경로는 헤더를 요구하지 않는다(하위호환) |

## 7. 검증

브라우저 없이 확인 가능한 것부터.

1. **게이트 전 무기록**: REQUIRE_ZONE 런을 띄우고 평면도 도착 후 30초 대기 → 대상 스트림 파일의
   크기·mtime 이 런 시작 전과 동일한지. (원인 B 회귀 검사)
2. **이른 주입 거절**: 평면도 발행 전에 `POST /inject/zone` → 409 이고 명령 파일이 0바이트 그대로인지.
3. **헤더·토큰**: 구역 확정 후 스트림 첫 줄이 헤더 레코드이고 `run_id` 가 `/run` 응답과 같은지,
   `zone` 이 조작자가 보낸 좌표와 같은지.
4. **abort 보존**: 게이트 중 abort → 기존 녹화본의 체크섬 불변.
5. **UI 로직**: 이 저장소에서 쓰던 quickjs + DOM 스텁 하니스로 run_id 분기·거절 경로를 검사한다
   (브라우저 없이 돈다).
6. **회귀**: 비대화형 렌더 1 케이스가 종전대로 산출물을 만드는지(`regen_router_cases.sh <case>` 1건).

## 8. 미해결로 남기는 것

- **원인 C 의 출처.** 조건은 §4-D 로 막았지만 왜 14 ms 만에 주입이 도착했는지는 모른다. 재현되면
  브라우저 콘솔의 네트워크 기록이 필요하다.
- 옛 녹화본에는 헤더 레코드가 없다. `Load previous recording` 은 종전대로 동작하며, 그 화면이
  "자동 주입" 배지를 붙이는 기존 동작을 유지한다.
