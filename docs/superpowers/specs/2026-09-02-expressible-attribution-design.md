# 설계: `expressible` 의 귀속 — 두 질문을 한 호출에서 받는다

작성 2026-09-02 00:51. 선행 레인: S1(`2026-08-31`), S2(`2026-09-01`), cargo-ban(`2026-09-01`, 진행중).
이 문서의 모든 인용은 재검증했고, **인용 가능한 것과 불가능한 것을 §2 에서 갈라 적는다.**

## 0. 이 문서가 답하는 물음

> 모델이 OOD 사건에서 `expressible=true` 를 내는 원인이 **둘**인데, 지금 그 둘을 못 가른다.
>
> * **원인 A — 메뉴 artifact.** `no_intervention` 이 언제나 메뉴에 있고 무엇이든 "아무것도 안
>   함" 으로 표현하므로, "이 메뉴로 원인을 없앨 수 있나" 는 구조적으로 `true` 쪽으로 편향된다.
> * **원인 B — 사실 부재.** 모델이 받은 입력에 "이 배선이 비싸다" 는 값이 없다. 55% SoC 만
>   보면 *"sufficient for continued operation"* 은 반박 불가한 독해다.
>
> 두 표면을 동시에 바꾸면 `expressible` 이 뒤집혀도 **무엇 때문인지 말할 수 없다.**

### 사용자 결정

|---|---|---|
| **D-1** | 두 질문을 **한 호출에서 둘 다 받는다**(필드 분리). 순차 2단계도, 한쪽만 바꾸기도 아니다 | 유료 호출 1회로 2×2 를 얻고, 대조가 **같은 샘플 안**에 있다 |

## 1. 왜 지금인가 — 대조군이 90분 전에 사라졌다

`2633d855`(2026-09-01 23:09) 가 `_EXPRESSIBLE_DESC` 의 **질문 범위에서 NOOP 을 뺐다**:

```
- false if NOTHING in this tool menu can remove the CAUSE of what you observed -- ...
+ false if NOTHING in this tool menu OTHER THAN NOOP can remove the CAUSE of what you
+ observed -- ... NOOP changes nothing, so it never counts as a way to remove a cause. ...
```

그 커밋은 자기 대가를 정직하게 적었다: **"옛 문구의 3/3 실측(2026-08-29)은 이 문구의 성적이
아니다 — 어휘 밖 3건 + 대조군을 산 호출로 다시 재기 전까지 인용하면 안 된다."**

⟹ 그 말이 맞고, 결과는 이렇다. **디스크의 모든 녹화(S1 의 115/115 · 6/6 포함)는 옛 문구로
받은 답이고, 새 문구로 받을 답과 비교할 축이 없다.** 원인 A 의 크기를 재려면 두 문구를
나란히 물어야 하는데, 지금은 하나만 물을 수 있다.

**이 레인은 그 대조군을 되돌림 없이 복원한다** — 옛 문구를 **두 번째 필드**로 되살려, 한 호출
안에서 두 질문의 답을 동시에 받는다. 두 필드의 차이가 곧 **원인 A 의 크기**다.

## 2. 사실 — 인용해도 되는 것과 안 되는 것

### 2-1. 인용 가능

| 사실 | 출처 | 상태 |
|---|---|---|
| S1 의 두 OOD 레인에서 `expressible` 이 전부 `True`(zone 115/115, mild 6/6, 프로브·음성대조 포함) | `2026-08-31-s1-…` 보고서 §2 | 옛 문구 하에서의 관측 |
| 노골 프로브에서 모델의 **산문이 필드와 정면으로 모순**됐고, 기전은 "`no_intervention` 은 언제나 available 하고 무엇이든 표현한다" | `2026-08-30-minted-tool-enactment.md` | n=3, 모델 1, 프롬프트 1 |
| 재배정 창은 `closed ≈ 247/287` 에서 닫히고 **S1 의 mild 보드 결정은 `closed=259`** | S2 spec §1-4 | 한 판(seed 1, OOD seed 7) |
| 새 키를 `COMMON_ARGS` 에 더하면 **자동으로 필수**가 되어, 빠지면 `missing_args` 거절 | `tool_registry.py:62-66` 코드 | §3-3 이 이것 때문에 존재한다 |

### 2-2. 🔴 인용 금지

* **"개정 문구가 어휘 밖 사건 3/3 을 잡는다"(2026-08-29)** — 그 3/3 은 `2633d855` **이전**
  문구의 성적이다. 현행 문구는 아직 산 호출로 재인 적이 없다.
* **`expressible == False` 비율을 성공 지표로** — `_EXPRESSIBLE_DESC` 주석이 직접 적듯 그
  비율은 부분적으로 **프롬프트 준수**를 잰다. 세대를 가르는 키는 `decision_source` 다.
* **S1 의 "mild 에서 모델이 착각했다"** — 그 보드는 창 밖(`closed=259`)이라 NOOP 이 정직한
  답이었다. 착각인지 아닌지는 **창 안 사건에서만** 갈린다(이 레인의 범위 밖, §6).

## 3. 설계

### 3-1. 필드는 둘, 질문도 둘

| 필드 | 묻는 것 | 쓰임 |
|---|---|---|
| `expressible` (기존) | "**NOOP 을 뺀** 메뉴로 원인을 없앨 수 있나" | **결정에 쓰인다.** L2 합성은 이 필드가 `False` 일 때만 발화한다(`synthesize.py:612`) |
| `menu_expressible` (신규) | "**메뉴 전체로**(NOOP 포함) 원인을 없앨 수 있나" | **측정에만 쓰인다.** 옛 녹화와의 비교축이고, 결정에는 절대 안 들어간다 |

**두 필드의 차이가 원인 A 의 크기다.**

| `expressible` | `menu_expressible` | 읽는 법 |
|---|---|---|
| `False` | `True` | **메뉴 artifact 가 실재한다** — NOOP 이 있어서 "표현 가능" 이 됐던 사건 |
| `False` | `False` | 메뉴와 무관하게 어휘 밖 — 가장 강한 L2 발화 근거 |
| `True` | `True` | 개입이 정말 불필요하거나, 원인 B(사실 부재) |
| `True` | `False` | 🔴 **모순** — 좁은 메뉴가 되는데 넓은 메뉴가 안 된다. 발생하면 그 자체가 보고 대상 |

### 3-2. 옛 문구는 **바이트 그대로** 박는다

`menu_expressible` 의 description 은 `2633d855` **직전**의 `_EXPRESSIBLE_DESC` 문자열을
글자 그대로 쓴다. 비교축이 성립하려면 옛 녹화가 받은 질문과 **같은 질문**이어야 한다.

🔴 **두 description 을 공통 상수에서 유도하지 않는다.** 유도하면 `expressible` 을 고칠 때
비교축이 조용히 따라 움직인다. 두 벌로 두되, 게이트가 옛 문구의 **바이트 동일성**을 못박는다
(§5 G-2). 이 레포에서 "두 벌은 갈린다" 는 원칙의 **예외**이고, 그 이유를 코드 주석에 적는다.

### 3-3. 🔴 필수 인자가 아니라 **선택 인자**여야 한다

`check_tool_args` 는 `want = set(COMMON_ARGS(valid)) | {…}` 로 **필수 키 집합**을 만들고,
`missing = want - set(args)` 가 비지 않으면 거절한다. 동시에 `off_schema_args` 가 `want` 밖의
키를 거절하므로, **새 키는 `COMMON_ARGS` 안에 있어야 받아지는데 있으면 필수가 된다.**

⟹ 측정용 필드 하나가 **런을 죽일 수 있는 자리에 놓인다.** 받아들일 수 없다.

**설계:** `COMMON_ARGS` 를 필수/선택으로 가른다.

```
COMMON_ARGS(emitted)          -> 스키마에 실리는 전체(모델에게 보이는 것)  = 필수 ∪ 선택
COMMON_ARGS_REQUIRED(emitted) -> check_tool_args 의 `want` 가 쓰는 것      = 지금의 넷
COMMON_ARGS_OPTIONAL          -> {"menu_expressible"}
```

* `missing` 판정은 **필수**만 본다 → 빠져도 거절이 아니다.
* `off_schema_args` 판정은 **전체**를 본다 → 선택 키는 실려도 정상.
* 타입 검사는 **실려 있을 때만** 한다(`menu_expressible_not_a_bool`), 검사 순서는 기존
  `expressible_not_a_bool` **바로 뒤**에 넣는다 — 앞의 순서는 리뷰가 실측으로 고정했으므로
  건드리지 않는다.

### 3-4. 삼상 규약 — 안 실리면 `None`

`menu_expressible` 이 없으면 그 사건에서 **못 쟀다**(`None`)이지 `False` 가 아니다. 응답
페이로드에도 그 구별이 살아야 한다. 🔴 **빠진 것을 `False` 로 접으면 §3-1 의 표에서 "메뉴
artifact 가 실재한다" 칸이 거짓으로 부풀어 오른다** — 이 레인이 재려는 바로 그 값이다.

### 3-5. Julia 로는 이 레인에서 안 넘긴다

`policy_entry` 의 성공 분기가 키를 **손으로** 들고 있어서(`2026-08-29-…-plan-b.md` §4 가 기록),
새 키를 결정행에 실으려면 Julia 를 고쳐야 한다. 이 레인은 **Python 까지만** 간다:
서비스가 받고, 응답에 싣고, 게이트가 못박는다. 결정행 배선은 §6(Wave 2).

**그래도 이 레인만으로 쓸모가 있다** — 유료 프로브가 서비스 응답을 직접 읽으므로, 원인 A 의
크기는 결정행 없이도 잴 수 있다.

## 4. 하지 않는 것 (YAGNI)

* **`2633d855` 을 되돌리지 않는다.** 현행 문구가 결정에 쓰이는 문구다(D-1a).
* **`no_intervention` 을 메뉴에서 빼지 않는다**(D-1, S2 spec). `tool_choice="required"` 판에서
  `expressible=False` 를 나르는 운반체가 그 tool 하나뿐이라, 빼면 신고 채널 자체가 사라진다.
* **`synthesize.py` 의 발화 조건을 안 바꾼다.** L2 는 계속 `expressible == False` 에서만 쏜다.
  `menu_expressible` 은 **결정에 절대 안 들어간다**(§3-1).
* **사실 블록에 손대지 않는다**(D-2) — 넣을 값 둘이 다 Julia 쪽에서 와야 한다(§6).
* **비율로 성공을 주장하지 않는다**(§2-2).

## 7. 미측정 · 위험

1. **모델이 선택 필드를 실제로 채우는가 — 미측정.** 안 채우면 `None` 이 쌓이고 대조가 비는데,
   그건 결함이 아니라 관측이다(§3-4). 첫 유료 라운드에서 채움률을 함께 보고한다.
2. **필드 하나가 늘면 다른 필드의 품질이 떨어지는가 — 미측정.** 스키마가 길어지는 대가는
   잰 적이 없다. `macro`/`ranking` 의 형식 유효율을 같은 라운드에서 대조한다.
3. **두 질문이 서로를 오염시키는가 — 미측정.** 한 호출 안에 두 개를 물으면 모델이 둘을
   일관되게 만들려 할 수 있다(§3-1 표의 "모순" 칸이 0 이면 그 의심이 커진다).
   별도 호출 대조가 필요해지면 그때 잰다 — 지금 미리 하지 않는다.
4. **파일 경합.** `tool_registry.py` 는 `2633d855`(23:09) 이후 미커밋 변경이 없다(확인함).
   그러나 같은 브랜치에서 cargo-ban 레인이 동시에 커밋 중이므로, 집행 직전에 다시 확인한다.
   ⚠️ cargo-ban 은 Julia + `primitive_registry.json` 만 만지고 이 레인은 Python 한 파일만
   만진다 — 파일 교집합 0 을 확인했다. 공유 위험은 `test/runtests.jl` 인데 **이 레인은 거기
   등록을 추가하지 않는다**(기존 pytest 파일에 시험을 얹는다).
