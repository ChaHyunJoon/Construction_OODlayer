# 30시드 630판 병렬 스윕 결과 (D=20, 2026-08-13)

> **세대 표시** — 이 문서는 **현행 세대**다. 창고 거리 `D=20.0`, 행동 어휘 `[0,1,2,3,4,7,8]`
> (매크로 7 RelocateBuild · 8 SwapBattery 포함), 학습셋 `oracle/out/n44_plus78.jsonl`.
> 원자료 `results_4pol/*.jsonl` (case 당 90행), 리포트 `artifacts_4pol/`.
> 이전 최신 문서였던 `RESULTS_D20_2026-08-12.md` 는 같은 기하지만 **n=5** 였다. 이 문서가 n=30 이다.

## 0. 한 문단 요약

7개 OOD case 를 30시드 × 3정책 = **630판** 돌렸다. **적응하지 않는 바닥선(`noop`)은 7개 중 6개
case 에서 빌드를 끝내지 못한다**(완주율 0~7%). 두 적응 정책은 그 실패를 뒤집는다 —
`surrogate` 91.0%, `dspy` 90.5% (210판씩). 완주율만 보면 둘은 무승부지만, **완주에 드는
개입비용과 makespan 에서는 `dspy` 가 7개 case 전부에서 `surrogate` 를 이긴다**
(비용 1.2~5.0배 저렴, makespan 2.8~20.0% 단축).

별도로 `oracle` 레인을 **이번에 처음 실행 가능하게 만들었다**(그동안은 배선이 없어 조용히
`canonical` 로 폴백하고 있었다 — 결정 적중률 0/4). 같은 분모(7 case × 30 seed = 210판)에서
완주율 **98.1% [95,99]**, **6개 case 가 30/30** 이다(§5.3.5). 남은 미완주 4판은 원인이
규명된 별개의 livelock 이며, 그것이 정직하게 정체로 보고되는 것이 올바른 동작이다.

가는 길에 **에러 없이 그럴듯한 숫자로 새던 결함 3건**을 잡았다(§5.3.4, §6): surrogate 레인이
조용히 canonical 로 폴백하던 회귀, 빈 샤드가 `OK` 로 보고되던 경로, 그리고 평가 엔진이
복구 예산을 환급하지 않아 엔드게임에서 빌드를 못 끝내던 결함.

**읽는 법 세 가지.**

1. **적응이 완주를 만든다.** `battery` 를 뺀 6개 case 에서 `noop` 의 CI 상한(11~21%)이 두 적응
   정책의 CI 하한(59~89%)과 **겹치지 않는다.** n=30 이 사 준 것이 이것이다 — n=5 에서는 이
   분리를 주장할 수 없었다.
2. **`battery` 는 OOD 가 아니다(이 설정에서는).** `noop` 조차 100% 완주한다. 즉 배터리 사건은
   개입 없이도 빌드가 끝난다 — 이 case 에서 정책을 가르는 것은 완주가 아니라 **비용**이다(§3).
3. **surrogate 와 dspy 는 서로 다른 곳에서 이긴다.** surrogate 는 단일축(`fault`,
   `fault_battery`)에서 100%, dspy 는 조합축(`all`, `battery_zone`)에서 앞선다. 이는 설계
   서사와 맞는다 — surrogate 는 단일축 격자로 학습됐고, LLM 은 처음 보는 조합에 일반화한다.
   다만 case 별 차이는 CI 가 넓게 겹치므로 **case 단위로는 유의하다고 말할 수 없다.**
   전체 210판 대비(91.0% vs 90.5%)는 사실상 동률이다.

가장 선명한 사례는 `battery` 다. 두 정책 다 30/30 완주하지만 **고른 팔이 다르다**:

이것은 어휘 문제가 **아니다.** `test_surrogate_support.py` 가 `support=[0,1,2,3,4,7,8]` 을 확인하므로
surrogate 의 학습셋에는 `SwapBattery`(8) 근거가 있다 — **고를 수 있는데 안 고른다.**
남은 설명은 학습셋의 라벨 분포이며, 이 스윕은 그 지점을 특정해 준다.

## 4. 이 결과를 믿을 수 있는 이유 (기계 검증 4종)

숫자보다 먼저 볼 것. 전부 **주장이 아니라 실행 가능한 검사**다.

| 검사 | 명령 | 결과 |
|---|---|---|
| 판 수 완전성 | `merge_shards.py` | rc=0, **case 당 90/90 행** — 빠진 (seed, policy) 0건 |
| 기하 세대 | `check_geometry.py --expect-depot-distance 20.0` | rc=0, **630행 전부 D=20** |
| **레인 무결성** | `check_lanes.py` | rc=0, **630행 3818결정 전부 `policy == enacted`** |
| 사전 조건 | `gate_prereq.sh 16` | P1·P2·P9·P3·P4·P8 전부 통과 (P8 동시 16요청 **16/16**) |

**레인 무결성 검사가 이번에 새로 생긴 이유는 §6 에 있다.** 이 스윕 직전, `surrogate` 라고 적힌
판이 실제로는 `canonical` 을 집행하고 있었다.

### 4.1 병렬이 결과를 바꾸지 않았다는 사전 증거 (P7 게이트)

`zone`/seed 1/`noop` 을 **단독 8판**과 **K=16 부하 하 8판** 돌려 비교했다
(`_night/gate_p7_result.md`).

```
PASS  sim_seconds: 양쪽 모두 상수 123.9 -- 검정 생략
PASS  closed:      양쪽 모두 상수 263   -- 검정 생략
PASS  complete:    Fisher exact p=1.0000 (단독 0/8 / 부하 0/8)
```

16판이 전부 같은 값이었다. 그러나 **이 게이트의 증거력은 rc=0 이 시사하는 것보다 훨씬 약하다.
아래 한계를 읽지 않고 이 결과를 인용하지 말 것.**

**한계 1 — 통계 검정이 사실상 한 번도 실행되지 않았다.** 양쪽 표본이 상수라
`compare_continuous` 의 조기 반환("양쪽 모두 상수 → 검정 생략")이 걸려 `mannwhitneyu` 가 아예
돌지 않았다. `complete` 도 양쪽 모두 전판 미완주라 Fisher p=1.0 은 구성상 나온 값이다.
즉 **rc=0 은 "세 비교가 전부 생략되거나 퇴화했다"는 뜻**이지 "부하 효과가 없음이 검정됐다"가 아니다.

**한계 2 — 하필 부하 효과가 나타날 수 없는 칸을 골랐다.** 측정 칸은 `zone`/seed 1/**`noop`** 이다.
`noop` 은 개입하지 않고 **DSPy 서비스와 통신하지 않는 유일한 레인**이다. K=16 에서 실제로
우려되는 부하 효과 — HTTP 지연과 API 경합이 `dspy` 레인의 결정 타이밍을 흔드는 것 — 은
이 칸이 정의상 배제한다. LLM 이 끼지 않는 칸을 고른 것은 "부하 효과와 API 지연을 섞지 않기
위해서"였지만, 결과적으로 **재고 싶었던 효과 자체를 빼고 쟀다.**

**한계 3 — 이 판은 완주하지도 않는다**(0/8, `closed` 상수 263). 교착 상태에서 멈춘 판이
반복 실행에서 같은 값을 낸다는 것은, 활발히 진행되는 판이 그렇다는 것보다 훨씬 약한 진술이다.

따라서 **"이 저장소의 비결정성이 시뮬레이터 코어 밖에 있다"고 결론짓지 않는다.** 이 16판이
보여준 것은 `zone`/seed 1/`noop` 이라는 **한 개의 교착 칸이 부하 아래에서 결정적**이라는 사실뿐이다.
비결정성 규명에는 여전히 완주하는 칸과 `dspy` 레인을 포함한 별도 설계가 필요하다.

**그럼에도 병렬 진행을 정당화하는 근거는 따로 있다**(§4 의 레인 검사 630행 3818결정 전부 통과,
샤드 fail 0). P7 은 그 근거의 **보조**이지 주된 근거가 아니다.

## 5. `oracle` 레인 — 이번에 처음으로 **실행 가능해졌다**

§5 는 별도 워크스트림의 결과다. 원자료는 `results_oracle{,_v2,_v3}/*.jsonl`, 관련 커밋은
`d318d1d`(레인 신설) · `2b54668`(matrix v2 격자) · `df92c37`(zone 상태 게이트) ·
`bffaa52`(실시간 술어) · `6f5bc7b`(예산 환급).

### 5.1 오라클은 정책으로 존재하지 않았다

`DEMO_POLICY=oracle` 은 지금까지 **실행 레인이 아니었다.** `policy.jl` 에 `pol["oracle"]` 이 없어
존재 검사가 실패하고 `enacted = "canonical"` 로 조용히 덮어써졌다 — 경고도 종료코드도 없이
요약 행만 `"policy":"oracle"` 로 남았다. 실측 증상: a\* 대비 결정 적중률 **0/4**
(정의상 4/4 여야 하는 레인).

즉 "오라클이 빌드를 못 끝낸다"의 1차 원인은 완주가 아니라 **레인이 배선조차 안 된 것**이었다.

### 5.2 배선한 뒤 드러난 진짜 문제

레인을 만들자 `enacted=oracle`, 적중률 4/4 가 나왔다. 그런데 `fault_zone` 이 **`closed=186/313`
에서 교착**했다 — 같은 case·seed 에서 `canonical` 은 291/313 로 완주하는데.
**a\* 를 충실히 집행한 결과가 미완주였다.**

갈린 결정은 단 하나, `closed=99` 의 `ZoneTruth` 에서 canonical `NOOP` vs a\* `RelocateBuild`.

판별자는 **이력**이었다. `zone` s1 과 `battery_zone` s1 은 `RelocateBuild` 로도 완주하는데
`fault_zone` s1 만 죽는다. `zone_primitives` 는 사실상 동일하다. 차이는 `fault_zone` 이
`closed=58` 에서 `Replace`(`hot_swap_robot! :via_depot`)를 실행해 **`RECOVERY_SPARES` 가 차
있었다**는 것 — 그 상태에서 빌드를 통째로 옮기면 이송 중인 운반체가 교착한다
(`verifier.jl` 의 "while carriers are mid-transit" 와 같은 기전).
복구 사다리 상한 문제가 아니다: `--reform-max 12` 는 186 → 191 로 여전히 stall.

### 5.3 수정과 결과

`oracle_macro` 의 ZoneTruth 가지에 **상태 게이트**를 넣었다. 개입 사유(`n_nav_blocked>0 &&
root_covered==0`)는 그대로 두고 실행가능성을 상태로 판정한다 — `RelocateBuild` 는
`RECOVERY_SPARES` 가 비고 `relocate_feasible` 일 때만, `ForbidZone` 은 `n_restage_feasible>0`
일 때만, 아니면 `NOOP`. 이 원칙은 이미 저장소에 문장으로 있었다(`dspy_service.py:96`:
"legal 은 kind 가 아니라 그 순간 그 팔이 실제로 무언가를 할 수 있는가로 정해져야 한다").

1차 확인: 7 case × 3 seed = **21판 전부 완주**. 그러나 21판은 완주**율**이 아니므로, 본 스윕과
같은 분모로 다시 쟀다.

### 5.3.2 남은 실패의 기전 (실측으로 특정됨)

미완주 8판의 결정열은 **전부 같은 형태**다:

```
seed=14  closed=285
  ZoneTruth  -> RelocateBuild      # 아직 Replace 전. 정상 개입
  FaultTruth -> Replace            # 여기서 RECOVERY_SPARES 가 채워진다
  ZoneTruth  -> NOOP               # 게이트가 막는다
  ZoneTruth  -> NOOP               #   "
  ReformTruth-> ReformTeam  x6     # 막힌 내비 목표가 복구되지 않아 복구 사다리가 연속 발화
```

대조로, 완주하는 판은 zone 사건이 **Replace 앞에** 몰려 있어 전부 `RelocateBuild` 를 받는다
(seed 2: zone ×3 전부 RelocateBuild, ReformTeam 1회로 끝, `closed=291`).

집계: "Replace 이후 ZoneTruth → NOOP" 이 있는 판은 **미완주 7/8 vs 완주 10/22**.

**원인**: §5.3 의 게이트는 `!isempty(CB.recovery_spares())` 로 판정하는데,
`src/respec/ood_injection.jl:787-795` 의 `RECOVERY_SPARES` 는 **`push!` 와 `empty!` 만 있고
스페어가 도착할 때 제거하는 경로가 없다.** 게다가 `replace_robot.jl:1182/1271` 의 일반
spare-splice 경로도 이 집합을 채운다. 즉 이 술어가 실제로 재는 것은 "지금 이송 중인가"가 아니라
**"이 판에서 Replace 가 한 번이라도 있었는가"** — 되돌아오지 않는 단방향 래치다.
그래서 Replace 이후의 모든 zone 사건이 영구히 `NOOP` 으로 떨어진다.

이 실패 양식은 전체 브랜치 리뷰가 **코드만 보고 예측**했고, 이 210판이 그 상관을 실측으로 보였다.

### 5.3.4 `closed=285` 의 정체 — 복구 예산 소진 (규명 완료)

**420판 전체에서 성립하는 법칙:**

| | 판수 | 정체 |
|---|---|---|
| ReformTeam 단을 **6단 미만** 쓴 판 | 402 | **0** |
| **정확히 6단**을 쓴 판 | 18 | **18** |

`--reform-max` 기본값이 **6** 이다(`llm_ood_eval.py:498` → `DEMO_REFORM_MAX`).
**두 스윕의 정체 18건이 전부 예산을 끝까지 썼고, 예산이 남은 판은 하나도 정체하지 않았다.**

**기전.** `recover_stalled_teams!`(`replace_robot.jl:583-697`)는 단발 복구가 아니라
**내부 상태를 가진 사다리**이며 호출당 한 단만 오른다. 루트 `DepositCargo` 를 닫는 마지막 단
(`force_advance_stuck_carrier!` → `:carrier_closed`)은 `SNAP_COUNT[] >= 3` 이어야 도달 가능하므로
**최소 4단이 먼저 발화해야 한다.** 이 단이 필요한 판은 5~8단을 쓰는데 6단만 받는다.

**결정적 결함**: `tools/monitor/run_demo.jl` 은 `_REFORM_CT[]` 를 올리기만 하고 **되돌리지 않는다.**
형제 엔진 `tools/monitor/render_demo.jl:566-571` 은 빌드가 전진하면 예산을 환급하며, 주석에 이유가
적혀 있다 — 예산은 **헛돈 반복**을 막으려는 것이지 총 복구 횟수를 제한하려는 것이 아니다.
**평가 엔진이 그 규칙의 절반을 잃어버렸다.** 그래서 중반에 쓴 복구가 엔드게임에서 영구 차감된다.

**결정적 실험**: 285 에서 멈추던 `fault_zone` 시드 14·19·21·27·29 를 `--reform-max` 만 20으로
바꿔 재실행 → **5판 전부 291 완주.** 앞 6단 궤적은 바이트 단위로 동일하고 7·8단이 이어질 뿐이다.
게다가 **완주하는 판들도 285 를 지나간다**(`no_team@285, carrier_closed@286`) —
**285 는 교착점이 아니라 `fault_zone` 엔드게임 사다리의 정규 경유역이고, 거기 도달할 때 예산이
1단 이하로 남은 판만 멈춘다.** 그래서 숫자가 그토록 반복됐다.
교착 시점에 22대 중 1대만 운반 중이고 7/8 조립체가 `done`, `spares_left=11` — **고갈된 자원은 없다.**

**수정(`6f5bc7b`)**: `--reform-max` 를 키우지 않는다 — 그건 곡선맞춤이고 진짜 livelock 을 20단

일치시킨다. 상한의 의미가 "총 N회"에서 **"연속 N회 헛돔"** 으로 바뀐다. 새 상수는 없다.

## 6. 이 스윕 직전에 잡은 결함 두 개

둘 다 **에러 없이 그럴듯한 숫자로 새는** 종류다. 이 저장소의 특징적 실패 양식이다.

### 6.1 `surrogate` 레인이 조용히 `canonical` 이었다 (회귀, 치명)

`dspy` 가 **3.2.1 → 3.3.0** 으로 올라가면서 `dspy/utils/lazy_import.py` 가
`sys.modules["numpy"]` 에 지연 프록시를 심는다. 그 뒤 서비스의 `_load_surrogate()` 가
sklearn → joblib → numpy 를 부르면 반쯤 초기화된 `numpy._core` 로 재진입해
`numpy/_core/_methods.py:17` 의 `mu.dtype("bool")` 에서 죽는다:

```
TypeError: data type 'bool' not understood
```

예외는 `surro_error` 로 삼켜져 **서비스가 정상 기동한다.** 그러면 `/macro` 의 surrogate 블록에
error 가 실리고, `policy.jl` 이 `available=false` 로 보고 `enacted="canonical"` 로 바꾼다 —
요약 행은 `"policy":"surrogate"` 라고 적는데 결정은 전부 canonical.

- **증거**: 수정 전 샤드의 surrogate 행 `enacted: ['canonical']×4`.
  격리된 D=40 구세대 행은 전부 `enacted: surrogate` → 회귀가 맞다.
- **수정**: `dspy_service.py` 에서 `import dspy` **앞에** numpy·sklearn 을 실제로 import.
- **재발 방지**: `gate_prereq.sh` 에 **P9** 추가 — `/health.surrogate` 가 `ERROR` 로 시작하면 exit 1.
  P9 가 실제로 발동하고 복구 후 통과함을 양방향 확인했다.
- **영향 범위**: 이 스윕은 수정 후 전량 새로 돌았다. **630판 중 오염된 판은 0개**(§4 레인 검사).

### 6.2 빈 샤드가 `OK` 로 보고되던 경로

`run_shard.sh` 의 `have=$(grep -c . "$f" 2>/dev/null || echo 0)` 는 안전해 보이지만 아니다.
`grep -c` 는 **0매치에도 "0" 을 출력하고 rc=1 로 끝나므로** `||` 분기가 함께 발동해 `"0\n0"` 이
캡처된다. 그러면 완주 판정 `[ "$rows" -lt "$N_POLICIES" ]` 가 "integer expression expected" 로
거짓이 되어 **빈 `rows.jsonl` 을 가진 샤드가 `[shard] OK` 로 보고된다.**
밤새 도는 210샤드에서 이것은 조용한 데이터 손실이다. 구현 전에 잡아 고쳤다.

`run_4pol.sh`(순차 경로)는 **수정하지 않았다** — 순차 재현 경로로 보존돼 있다.

## 8. 이 문서가 주장하지 않는 것

- **완주율의 case 간 차이가 유의하다고 주장하지 않는다.** surrogate 91.0% vs dspy 90.5% 는
  동률이고, case 단위 차이는 CI 가 넓게 겹친다.
- **§3 의 비용·makespan 우위에 CI 를 붙이지 않았다.** 7/7 case 에서 같은 방향이라는 것이
  현재의 근거이며, 판별 검정은 하지 않았다.
- **oracle 이 "무조건" 완주한다고 주장하지 않는다.** n=30 실측은 **95.7% [92,98]** 이고,
  `fault_zone` 은 **73.3%** 다(§5.3.1). 원인은 **아직 규명되지 않았다** — 유력해 보였던 가설
  하나는 실험으로 반증됐다(§5.3.3).
  참고로 `md/README.md` §6 은 OOD 가 **없을 때의** 천장을 97%±3 으로 적는다 — 즉 5개 case 의
  30/30 은 그 천장에 닿아 있고, 남은 문제는 `fault_zone` 한 곳에 몰려 있다.
- **`noop` 이 100% 완주하는 `battery` 는 OOD 난이도가 낮다**는 뜻이며, 이 case 의 정책 비교는
  완주가 아니라 비용 축에서만 의미가 있다.

## 9. 산출물 provenance — 어느 트리에서 나온 숫자인가

이 문서의 숫자는 **두 개의 코드 상태**에서 나왔다. 섞어 읽으면 안 되므로 명시한다.

| 절 | 산출물 | 생성 시점의 HEAD | 비고 |
|---|---|---|---|
| §2·§3 (630판, 3정책) | `results_4pol/*.jsonl` | `bffaa52` **이전** | 예산 환급 수정(`6f5bc7b`) **전** |
| §5.3.1 (oracle v1) | `results_oracle/*.jsonl` | `df92c37` | zone 게이트 = 런범위 래치 |
| §5.3.3 (oracle v2) | `results_oracle_v2/*.jsonl` | `bffaa52` | zone 게이트 = 실시간 술어 |
| §5.3.5 (oracle v3) | `results_oracle_v3/` | `6f5bc7b` | **예산 환급 적용** |

**§2·§3 의 630판은 예산 환급 수정 이전 트리에서 나왔다.** 그 수정은 `run_demo.jl` 을 고치므로
원리적으로 `noop`·`surrogate`·`dspy` 에도 영향을 줄 수 있다. 그래서 확인했다.

**정합성 프로브 (7 case × 5 seed × 3 정책 = 105판, `results_4pol_reformfix/`)**:
수정 전 `results_4pol` 의 같은 시드 105판과 대조한 결과 —

| | 완주 |
|---|---|
| 수정 전 (`results_4pol`, 시드 1~5) | 68/105 |
| 수정 후 프로브 (`results_4pol_reformfix`) | **68/105** |

**21개 (case, policy) 쌍 전부에서 시드별 상태 변화가 0건이었다.** 즉 이 수정은 3정책 스윕의
결과를 바꾸지 않는다. 이유는 기전과 정합한다 — 예산 환급은 **복구 사다리의 도달 거리**만 늘리는데,
`noop` 은 애초에 개입하지 않아 사다리를 타지 않고(실패가 `closed` 174~263 에서 일찍 난다),
`surrogate`·`dspy` 의 실패는 예산 제약형(Mode A)이 아니었다.

같은 방향의 독립 증거: oracle v2 → v3 에서 `reference_policy.score()` 가 **0.9654 로 바이트 단위
동일**했다. 즉 이 수정은 **결정을 하나도 바꾸지 않고 도달 거리만 늘린다** — 외과적이다.

따라서:
- §2 의 **정책 간 비교는 유효하다** — 630판 전체가 하나의 동일한 트리에서 나왔다.
- §2 의 **절대 완주율도 현재 코드에서 유지될 것으로 보인다**(n=5 프로브 기준). 다만 프로브는
  검정력이 낮으므로, n=30 전면 재측정이 확정 근거다.

재측정은 같은 명령으로 가능하며, 샤드 provenance 스탬프(`4684aeb`) 덕분에 **커밋이 다르면
자동으로 재실행된다** — 옛 샤드가 조용히 SKIP 되어 섞이지 않는다.
