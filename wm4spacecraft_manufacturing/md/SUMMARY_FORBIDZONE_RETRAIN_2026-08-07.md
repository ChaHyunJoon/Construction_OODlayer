## 0. 30초 요약

로봇들이 트랙터를 조립하는 시뮬레이터가 있다. 조립 중에 사고(로봇 고장, 배터리 방전,
출입금지구역 발생)가 터지면 **누군가 "그럼 어떻게 할까"를 결정해야 한다.** 그 결정을
내리는 후보가 셋이다 — 규칙표, 학습된 모델(surrogate), LLM.

이번 작업 전에 두 가지가 이상했다:

1. **학습된 모델이 규칙표와 완전히 똑같은 답만 냈다.** 5판을 돌렸는데 결과가 글자 하나까지 같았다.
2. **`ForbidZone` 이라는 대응 행동이 한 번도 사용된 적이 없었다.** 코드에는 있는데 실제로는 안 쓰였다.

이번에 둘 다 원인을 찾아 고쳤고, **둘 다 측정으로 확인**했다.

| | 고치기 전 | 고친 후 |
|---|---|---|
| 학습 모델이 구역 사고에서 고른 행동 | `NOOP`(아무것도 안 함) × 7 | **`RelocateBuild`(빌드 통째 이동) × 7** |
| 구역 사고 정답률 | **0 / 7** | **7 / 7** |
| 전체 결정 정답률 | 32% | **68%** |
| 완주한 판의 조립 시간 | 66.3초 | **35.5초** |
| 에너지(노드당) | 971 J | **739 J** |
| `ForbidZone` 이 선택지로 제시된 적 | **한 번도 없음** | **있음**(이 저장소 최초) |

## 1. 용어 (여기만 읽으면 나머지가 읽힌다)

| 말 | 뜻 |
|---|---|
| **OOD 사고** | 계획에 없던 일. 여기서는 세 종류 — 로봇 고장 / 배터리 방전 / 출입금지구역 발생 |
| **매크로(macro)** | 사고에 대한 대응 행동. 번호가 붙어 있다 |
| **`NOOP`(0)** | 아무것도 안 한다. 공짜. 개입이 손해일 때 정답 |
| **`Replace`(1)** | 고장 로봇을 창고의 예비 로봇으로 통째 교체. 예비를 하나 소모 |
| **`ForbidZone`(3)** | 구역에 걸린 **부품 적치장만** 다른 자리로 옮긴다. 국소 수복 |
| **`RelocateBuild`(7)** | **조립 현장 전체를** 평행이동해 구역을 벗어난다. 가장 비싼 행동 |
| **`SwapBattery`(8)** | 로봇 몸체는 그대로 두고 **배터리만** 교체. `Replace` 보다 훨씬 쌈 |
| **surrogate** | 과거 시뮬 기록으로 학습한 모델. 0.1 ms 만에 답한다(시뮬 재실행은 수 분) |
| **canonical** | 사람이 손으로 쓴 규칙표. 학습 안 함 |
| **dspy / LLM** | gpt-4o 가 상황 설명을 읽고 고른다 |

## 2. 문제 1 — 학습 모델이 규칙표의 복사본이었다

### 무슨 일이었나

5판 전부에서 학습 모델과 규칙표가 **완주 여부·닫힌 노드 수·스텝 수·에너지·고른 행동 분포가
전부 같았다.** 우연이 아니었다.

### 원인 (버그가 아니라 데이터 문제)

학습 모델은 **학습 데이터에 한 번도 안 나온 행동은 후보에서 아예 빼버린다.** 근거 없이
점수를 매기는 건 추측이기 때문에, 일부러 그렇게 설계돼 있다.

그런데 배포된 학습 데이터에는 `SwapBattery`(8) 와 `RelocateBuild`(7) 행이 **한 줄도 없었다.**

```
배터리 사고 → 가능한 행동 [NOOP, Replace, Deprioritize, SwapBattery]
              모델이 점수 낼 수 있는 것 [NOOP, Replace, Deprioritize]   ← 8 탈락
구역 사고   → 가능한 행동 [NOOP, RelocateBuild]
              모델이 점수 낼 수 있는 것 [NOOP]                          ← 7 탈락, 선택지가 하나뿐!
```

구역 사고에서는 **고를 수 있는 게 `NOOP` 하나뿐**이었다. 모델이 절제를 선택한 게 아니라
**선택 자체가 불가능**했던 것이다. 그러니 규칙표와 같은 답이 나올 수밖에 없었다.

> **핵심 교훈.** 어휘가 빠지면 에러가 안 난다. **성능으로만 조용히 샌다.**
> 그래서 이제 `test_surrogate_support.py` 가 "배포 모델이 어떤 행동을 아는가"를 테스트로 강제한다.

### 어떻게 고쳤나

이미 있던 라벨 파일에서 빠진 행을 찾아 학습셋에 합쳤다.

| 학습셋 | instance 수 | 모델이 아는 행동 |
|---|---|---|
| `graded_hs_n44` (원래 배포본) | 44 | `[0,1,2,3,4]` |
| `n44_plus8` (+ 배터리 격자) | 62 | `[0,1,2,3,4,`**`8`**`]` |
| `n44_plus78` (+ 새로 만든 구역 격자) | 68 | `[0,1,2,3,4,`**`7`**`,`**`8`**`]` ← 현재 배포본 |

매크로 7 라벨은 없어서 **새로 만들었다** — 시뮬레이션 12판(순차, 68분).

### 결과

| 지표 | 재학습 전 | 재학습 후 |
|---|---|---|
| 고른 매크로 | `ReformTeam×30, Replace×12, NOOP×7` | `Replace×12, ReformTeam×10, **RelocateBuild×7**` |
| 구역 정답률 | 0/7 | **7/7** |
| 전체 정답률 | 32% (6/19) | **68% (13/19)** |
| 조립 시간 | 66.3 ± 1.3 초 | **35.5 ± 4.3 초** |
| 에너지 | 971 J/closed | **739 J/closed** |
| 완주율 | 80% | 80% (변화 없음) |

**"규칙표와 바이트 단위로 같다"는 기존 결론은 무너졌다.**

### 정직하게 함께 적어야 할 것 세 가지

**(1) 통계 검정은 여전히 5무다.** 그 검정이 `(완주 여부, 닫힌 노드 수)` 두 개만 비교하는데,
이 스트림에서 구역 축은 완주를 가르지 않기 때문이다. **"행동이 완전히 바뀌었다"와
"그 검정으로는 안 보인다"가 동시에 참이다.** 시드가 5개뿐이라 어차피 통계적 유의성은
원리적으로 못 얻는다(최소 p = 0.062). 그래서 방향과 크기만 보고한다.

**(2) 배터리 축은 안 움직였다.** `SwapBattery` 가 이제 점수는 받지만(후보에서 안 빠진다),
매번 `Replace` 보다 낮은 점수를 받는다(223.56 vs 248.15). 0/6 그대로다.
**이건 어휘 문제가 아니라 모델의 선호 문제**이고, 원인은 아직 모른다.

**(3) 매크로 개수를 정책끼리 직접 비교하면 안 된다.** 규칙표는 49번 결정했고 재학습 모델은
29번 결정했다(`ReformTeam` 30→10). 모델이 팀 재편성을 덜 하게 된 게 아니라,
**빌드가 빨라져서 교착 경보가 덜 울린 것**이다. 비교 가능한 분모는 채점된 19개뿐이다.

## 3. 문제 2 — `ForbidZone` 이 한 번도 안 쓰인 이유

### 무슨 일이었나

구역 사고에 대한 국소 수복 행동인데, 이 저장소 전체 측정 이력에서 **단 한 번도 선택지로
제시된 적이 없었다.** 기존 문서는 "빌드 도중에 구역이 뜨기 때문"이라고 적어 뒀다.

### 실제 원인 — 절반만 맞았다

`ForbidZone` 은 **아직 조립을 시작하지 않은** 부품 더미만 옮길 수 있다. 그런데 측정해 보니:

- 조립 시작 **전**(closed=0): 옮길 수 있는 부품 더미가 **7개** → `ForbidZone` 살아 있음
- 조립이 조금이라도 진행되면: **0개** → 죽은 행동

여기까지는 알려진 대로다. **진짜 문제는 그 다음이었다:**

> 이 시뮬레이터는 **첫 계산 배치에서 노드 58개를 한꺼번에 닫는다.**
> 그런데 사고를 예약하는 장치는 "노드 N개가 닫히면 터뜨려라" 방식이다.
> 그래서 1번이든 10번이든 40번이든 **전부 58에서 터진다.**
> 즉 `ForbidZone` 이 살아 있는 구간(0~약 46)에는 **애초에 도달할 방법이 없었다.**

프로브로 closed 1~120 을 4 간격으로 훑었는데 **첫 관측점이 이미 58**이었다. 그 아래는 관측
자체가 불가능하다. 이건 조정으로 해결되는 문제가 아니다.

| | 조립 시작 전 | 조립 시작 후(58~117 전 구간) |
|---|---|---|
| 옮길 수 있는 부품 더미 | **7** | **0** |
| 조건을 만족하는 구역 배치 | **238 / 426** | **0 / 300** |
| 진단 결과 | `forbid_zone` 238건 | `noop` 270건 |

### 어떻게 고쳤나 — 사람이 미리 정한다

**결론: 이 행동이 살아 있는 시점은 시뮬레이션 시작 전뿐이므로, 그 자리는 런타임에
"찾는" 게 아니라 사람이 **미리 정하는** 것이다.**

그래서:

1. 시뮬 시작 전 기하로 **후보 배치 426개를 미리 계산한 표**를 만들었다
   (`oracle/out/fz_presim.csv`). 각 행이 "여기에 이 크기로 구역을 놓으면 어떻게 되는가"다.
2. 사람이 그 표에서 한 줄을 고른다. 이번에 고른 것:
   `DEMO_ZONE_AT="3.6406,-1.2783,0.21"` — 항법 목표 5개를 막고, 세 행동(`NOOP`·
   `ForbidZone`·`RelocateBuild`)이 **모두 실행 가능한** 자리.
3. 시뮬 시작 전에 그 좌표에 구역을 심는다. **무작위 탐색 없음. 판이 시작될 때
   구역 위치가 이미 확정돼 있다.**

### 결과

```
valid = ["NOOP", "ForbidZone", "RelocateBuild"]     ← 이 저장소 최초
규칙표의 선택 = ForbidZone
실제 집행     = restage_all_blocked! + translate_whole_build! 1회 (residual=0)
```

**선택지로 제시되는 데 그치지 않고 실제로 집행까지 됐다.**

### 그런데 좋은 선택은 아니었다

같은 사고, 같은 좌표에서:

| 고른 행동 | 닫힌 노드 |
|---|---|
| `NOOP` | **205** / 313 |
| `ForbidZone` | **68** / 313 |

**개입했더니 더 일찍 멈췄다.** 그리고 LLM 은 같은 사고에서 `NOOP` 을 골랐다 — 규칙과 갈렸고,
이 판만 놓고 보면 LLM 쪽이 맞았다.

n=1 이라 결론은 아니다. 하지만 구분해서 기억할 가치가 있다:
**"선택지에 오른다"와 "정답이다"는 완전히 다른 문제다.** 이번 작업이 닫은 것은 앞의 것이다.

## 4. 작업 중에 발견한 것들 (계획에 없던 것)

이쪽이 더 중요할 수도 있다.

### 4-a. 막힘 술어가 학습 파이프라인에 아예 없다 ⚠️

이 저장소는 예전에 **"덮였다 ≠ 막혔다"** 를 실측으로 확립했다. 구역이 목표를 덮어도 로봇이
우회할 수 있으면 해롭지 않고, 진짜 문제는 **실제로 못 지나가게 막는가**다.

그런데:

- 라벨 생성기(`gen_oracle_dataset.jl`)에 `nav_blocked` 언급 **0건**
- 모델 입력(`e1_analyze.featurize`)이 읽는 구역 관련 값은 `zone_radius`·`zone_overlap`·
  `zone_root_cover` — **전부 "덮임" 계열**

즉 **결정을 가르는 진짜 변수가 학습 파이프라인에 실리지 않는다.** 매크로 7 라벨을 아무리
많이 만들어도, 모델이 구역 결정을 *제대로* 배우는 것은 구조적으로 막혀 있을 수 있다.
(이번엔 그래도 행동이 바뀌었지만, 그건 다른 특징으로 우회 학습한 것일 수 있다.)

**범위 밖이라 고치지 않았다. 다음 작업의 1순위 후보다.**

### 4-b. 학습/서빙 특징 불일치

`zone_root_cover` 열이 새로 만든 매크로 7 라벨 12행에는 **1.0** 으로 들어 있는데,
실제 서빙 시에는 그 값을 아무도 안 채워서 **-1** 이 들어간다. 즉 모델이 학습할 때 본 값과
실제로 받는 값이 다르다.

확인해 보니 두 값 모두에서 `RelocateBuild` 가 이기므로 **이번 결과는 유효하다.** 다만
그 여유를 지켜주는 장치가 없어서, 다음에 데이터를 합칠 때 이 열이 "출처 표시"로 변질돼
모델이 기하 대신 그걸 학습할 위험이 있다.

### 4-c. `verify.py` 의 V0 검사가 애초에 통과 불가능했다

검증 스크립트의 첫 검사가 "모든 사례가 7개 행동을 전부 굴렸는가"를 요구했는데,
`DS_VALID_ONLY` 로 만든 라벨은 **그 사고에서 말이 되는 행동만** 굴린다(고장 사고는 2개).
7개를 채우는 건 원리적으로 불가능했다.

배포 모델은 이미 "valid_mask 기준" 이라는 다른 판정을 쓰고 있었다. 검증과 배포가 서로 다른
기준을 쓰면 검증이 배포되지 않는 무언가를 검증하는 셈이라, **배포와 같은 판정으로 통일**했다.

`verify.py` : **7/8 → 8/8**

## 9. 이 작업에서 배운 것 한 가지

**"모델이 X 를 안 골랐다"와 "모델이 X 를 고를 수 없었다"는 완전히 다른 말인데,
요약 표에서는 똑같이 보인다.**

이번 두 문제가 정확히 그 형태였다. 학습 모델은 절제를 선택한 게 아니라 선택지가 하나뿐이었고,
`ForbidZone` 은 나쁜 행동이라 안 쓰인 게 아니라 제시된 적이 없었다. 둘 다 에러를 내지 않고
**성능 숫자로만** 샜다.

그래서 이제 두 가지가 테스트로 강제된다 —
`test_surrogate_support.py`(배포 모델이 어떤 행동을 아는가)와
`test_forbidzone_injector.jl`(그 행동이 실제로 메뉴에 오르는가).
숫자를 다시 재기 전에 이 둘을 먼저 돌리는 습관이 같은 함정을 막는다.
