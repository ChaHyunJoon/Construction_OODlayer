## The one finding that changes the plan

**The deployed novelty gate has a fold where it is not weak but inverted.**

`classify_report.py` splits leave-one-kind-out by held-out kind instead of averaging. Averaged, the
deployed score looks mediocre (AUROC 0.643). Split:

| held-out kind | `z_rms` (deployed) AUROC | OOD recall @95% |
|---|---|---|
| zoneblk | 0.974 | **95%** |
| fault | 0.878 | 57% |
| **battery** | **0.078** | **0%** |

Two consequences:

1. **The published "recall 0.94" is the zoneblk fold.** The deployed calibration is generated with
   `--exclude=zoneblk`, so that number describes precisely the fold where the score works. Not
   wrong — not representative. The fold average is ~50%.
2. **AUROC 0.078 is below chance by a wide margin, which means anti-correlated.** Held-out battery
   events score *more familiar* than known events. A novel battery disturbance is routed to the
   surrogate with confidence, every time. That is a live defect in what runs today.

`decision_margin` at AUROC 0.413 says the same thing from another angle: forest confidence points
the wrong way on novel input.

## Answers to the two questions from yesterday

**Can `ℓ` just be `Q̂(s,a)`?** Three forms, three answers — now measured, not argued:

| form | verdict |
|---|---|
| `Q̂` itself | No. A forest prediction is a mean of leaf values, so it is bounded by the training range and can never be extreme. CP thresholding is entirely about extremeness. |
| `\|Q̂ − y\|` alone | No, and already measured: `FINDINGS_ADWIN.md` — CUSUM on value-residual fired 4× with 3 spurious (8.6 / 7.8 on long streams). Residual magnitude tracks scenario difficulty, not novelty. |
| **two-model residual contrast** | **Yes.** `residual_contrast` scored the highest mean AUROC (0.726) and, uniquely, never collapsed on any fold (0.699–0.744). Post-hoc only — needs `y`. |

**Was the 30-seed urgency about the replay UI?** No — my reason was a throughput estimate, and your
objection defeats it: tonight's design determines the schema, so generating now guarantees
regenerating, and a test set produced before the design is frozen is not held out. Schema is now
frozen; generation comes after. Separately, the router is *not* replay-based: `route(env, truth)`
runs inside the sim loop on the live `env`; only the dashboard is a replay.

## Cheaper than expected

The nominal arm needs **no new simulation**. The control run (`inject=false`) already executes for
every instance for admissibility — today it is thrown away except for three summary columns. The
change adds an observation point to that existing run.

**Verified end to end** (`DS_NOMINAL=1 DS_SMOKE=1`, one fault instance, 6 rows written):

| row | kind | macro | fired | closed_at_fire | progress | valid_mask | nl_source |
|---|---|---|---|---|---|---|---|
| nominal | `none` | 0 | **False** | 58 | 0.185 | `[0]` | `nominal` |
| ×5 | `fault` | 0–4 | True | 58 | 0.185 | `[0,1]` | `captured` |

The nominal capture landed at **the same progress point as the disturbed runs** (closed 58 of 313),
which is the comparability property the design wanted — the control is the same world minus the
fired OOD, so it stops at the same batch boundary. `fired=False` means `load_df()` filters the row
out, so no existing analysis sees it.

*(Caveat now documented in code: `DS_NOMINAL_AT` is a target, not an exact trigger — the scheduler
checks at batch boundaries, so a target of 20 fired at 58.)*

## Throughput — measured, and my earlier estimate was wrong by 2×

One instance = 1 control + 5 macro runs = **757 s wall clock** (sum of `label_seconds` 726 s).
I had estimated ~400 s from the old 81 s/label figure. Actual per-run: control 212 s, macros
132 / 18 / 121 / 121 / 122 s.

Projection for the 30-seed held-out set (10 instances per seed, 24 new seeds = 240 instances):

| parallelism | wall clock |
|---|---|
| 1 | **50.5 h** |
| 4 | ~12.6 h |
| 8 | ~6.3 h |

Note the 4-way ceiling is memory, not CPU: `DS_STACK` defaults to 2 GB **per process**, and 4×2 GB
already OOM'd a 16 GB machine once. Going past 4 means lowering `DS_STACK` first and smoke-testing
for `StackOverflowError`. **This is not an overnight job at default settings** — it needs to be
planned as a multi-day background run or an explicit scope reduction.

## Why battery inverts — tested during the block, and it generalises

Re-checked with no train/cal/test split at all, so it is not a harness artifact (AUROC 0.049).
The descriptor medians explain it:

| kind | harm | resource_loss |
|---|---|---|
| fault | 1.000 | 1.000 |
| zoneblk | 0.374 | 0.000 |
| **battery** | **0.840** | **0.840** |

Fault and zoneblk sit at opposite extremes; battery sits **between** them. Calibrate on
{fault, zoneblk} and battery lands on the centroid of the calibration set.

> **A distance-based novelty score can only detect *extrapolative* novelty.**
> zoneblk held out → outside the hull → AUROC 1.000. battery → an interpolant → 0.049.

No metric change fixes this: full-covariance Mahalanobis moves battery only 0.049 → 0.272, because
the point really is in the middle. Detecting interpolative novelty needs a signal that can be large
in the *interior* of the input distribution — a **model-residual** signal. That is exactly why
`residual_contrast` reaches 0.744 on the battery fold.

**This reframes the whole score menu.** Distance and residual are not competitors to be ranked;
they detect **different kinds of novelty**. A deployable gate needs both — and since the residual
half currently needs the outcome, making it available at routing time (per-step scoring) moves from
"nice to have" to the critical path.

   | arm | battery | fault | zoneblk | known-acc |
   |---|---|---|---|---|

   Complementarity holds — battery 1% → 29% with no loss elsewhere, the first arm blind on no
   kind. The correction earns its place: dropping it buys 2 points of recall and pays 0.9 of
   known-accuracy, so part of any "combination wins" claim is just a looser threshold.
   **29% is still not deployable**, which is the concrete argument for the next item rather than
   a preference.
