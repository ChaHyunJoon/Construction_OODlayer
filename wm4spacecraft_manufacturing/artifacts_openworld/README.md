## 0. 먼저, 용어를 우리말로

제가 앞서 줄임말을 남발했습니다. 정리합니다.

| 줄임말 | 원래 말 | 우리말 | 무엇을 재는가 |
|---|---|---|---|
| **LOIO** | **L**eave-**O**ne-**I**nstance-**O**ut | **"한 상황 빼고 학습"** | 60개 상황 중 1개를 빼고 나머지로 학습 → 뺀 상황에서 채점, 60번 반복. **이미 아는 종류의 사고**를 얼마나 잘 처리하는가 |
| **LOKO** | **L**eave-**O**ne-**K**ind-**O**ut | **"한 종류 통째로 빼고 학습"** | 예: 배터리 사고를 하나도 안 보여주고 로봇고장·구역차단만으로 학습 → 배터리 사고에서 채점. **처음 보는 종류의 사고**를 얼마나 잘 처리하는가 |

두 이름 모두 기계학습의 표준 용어 **leave-one-out**(하나 빼고 학습해서 그 하나로 시험)에서 왔습니다.
`instance`(상황) 하나를 빼면 LOIO, `kind`(사고 종류) 하나를 통째로 빼면 LOKO입니다.
**빼는 단위가 다를 뿐 방식은 같습니다.**
| **regret (후회)** | **"최선 대비 손해"** | 0 = 매번 최선의 대응을 골랐다, 1 = 매번 최악을 골랐다 |
| **oracle (오라클)** | **"진짜 플래너로 전부 확인"** | 후보 대응을 하나씩 실제로 시뮬레이션해 정답을 확인. 항상 맞지만 한 번에 수십 초~분 |
| **surrogate (대리모델)** | **"학습된 근사 모델"** | 오라클 대신 0.1밀리초에 답을 내는 학습 모델. 공짜지만 틀릴 수 있음 |

**"미지 OOD 대응"의 정직한 시험이 바로 LOKO(한 종류 통째로 빼고 학습)입니다.** 지금까지 프로젝트의
모든 headline 숫자는 LOIO(아는 종류)로 측정된 것이었습니다.

### 게이트 관련 용어

"게이트"는 **"언제 비싼 진짜 플래너를 불러 확인할 것인가"**를 정하는 판단기입니다. 학습 모델은 공짜지만
처음 보는 상황에서 틀릴 수 있으니, 의심스러울 때만 플래너를 부르고 싶습니다. 무엇을 보고 의심할까요?

| 줄임말 | 우리말 | 판단 근거 |
|---|---|---|
| **covariate novelty** | **"입력 낯섦도"** | 지금 상황의 숫자들이 학습 때 보던 범위를 얼마나 벗어났는가. 벗어날수록 모델을 못 믿음 |
| **decision margin** | **"결정 마진"** | 1등 대응과 2등 대응의 점수 차이. 아슬아슬하면 뒤집히기 쉬움 |
| **disagreement** | **"모델 내부 이견"** | 학습된 모델은 결정트리 여러 개의 모임(forest)임. 그 나무들이 서로 다른 대응을 지지하면 = 모델 스스로 확신이 없음 |
| **무작위 (대조군)** | — | 같은 개수를 아무렇게나 골라 플래너로 넘김. **이걸 이겨야 신호가 진짜 정보를 담은 것** |

### "agnostic S3 FAIL"이 무슨 뜻이었나

- **`verify.py`** = 프로젝트의 자동 검증 시험지. V0·S1~S4·L1~L3의 8문항을 PASS/FAIL로 채점합니다.
- **S3** = "학습된 모델이 물리적으로 말이 되는 방향으로 반응하는가"를 보는 문항.
  예: *배터리가 더 많이 닳았으면 로봇 교체의 가치가 더 올라가야 한다.* 반대로 움직이면 FAIL.
- **agnostic** = 제가 새로 만든 특징 표현 방식(아래 2절).
- 즉 **"agnostic S3 FAIL"** = *"새 표현으로 학습했더니, 물리 상식 3문항 중 1문항에서 모델이 반대 방향으로
  반응했다"*는 뜻이었습니다. **데이터를 3배로 늘린 뒤 이 문제는 사라졌습니다(3/3 통과).**

## 2. 무엇을 고쳤는가 — 특징 표현

### 문제 진단

학습 모델에 넣는 입력이 **사고 종류 이름을 네 번 중복해서** 알려주고 있었습니다.

| 누출 경로 | 내용 |
|---|---|
| 종류 one-hot 4열 | 명시적으로 "이건 배터리 사고" 라고 알려줌 |
| `soc`(배터리잔량) | 배터리 사고가 아니면 전부 −1 |
| `zone_overlap`(구역겹침) | 구역 사고가 아니면 전부 −1 |
| `agent_pending`(밀린작업) | 구역 사고면 전부 −1 |

**−1 패턴만 봐도 종류가 100% 복원됩니다.** 그래서 처음 보는 종류가 오면 모델은 "학습 근거가 전혀 없는
좌표"를 받게 되고, 아무 말이나 하게 됩니다.

게다가 `severity`(심각도)는 **종류마다 의미가 뒤집혀** 있었습니다:

| 종류 | severity 의미 | 나쁜 방향 |
|---|---|---|
| 로봇 고장 | 1.0 심각 / 0.0 무해 | **클수록** 나쁨 |
| 배터리 | 사고 후 남은 잔량 | **작을수록** 나쁨 ← 반대! |
| 구역 차단 | 구역이 비켜난 정도 | 클수록 나쁨 |

로봇 고장에서 "심각도 높으면 개입"을 배운 모델은 배터리에서 **정확히 반대로** 행동합니다.

### 처방

종류 이름을 읽지 않고, 모든 종류에서 **같은 의미·같은 방향**을 갖는 물리량 6개로 다시 씁니다.

| 물리량 | 뜻 |
|---|---|
| `harm` | 이 사고가 얼마나 나쁜가 (0~1, 항상 클수록 나쁨) |
| `work_at_risk` | 남은 일 중 이 사고가 위협하는 비율 |
| `resource_loss` | 로봇 능력을 얼마나 잃는가 |
| `recovery_capacity` | 예비 로봇이 얼마나 여유 있는가 |
| `progress` | 언제 터졌는가 |
| `slack` | 일할 로봇이 얼마나 남았는가 |

핵심은 **"로봇 고장 = 배터리 잔량 0인 배터리 사고"**로 통합된다는 점입니다. 두 종류가 하나의 연속 축
위에 놓이면, 한쪽에서 배운 것이 다른 쪽으로 넘어갑니다.

이 설계는 부수적으로 **새 사고종류가 왔을 때 LLM이 할 일**도 바꿉니다: "새 DSL 종류를 발명하라"(불가능)
대신 **"관찰을 읽고 숫자 6개를 추정하라"**(LLM이 잘하는 일).

## 4. 안전 필터 — 무엇을 만들었나

### 발견한 두 가지 문제

1. **기존 "구역 지키기"는 제어가 아니라 순간이동이었습니다.** 로봇이 금지구역에 들어가면, 시뮬레이터가
   한 스텝 진행한 **뒤에 로봇 위치를 구역 경계로 강제로 옮깁니다.** 실제 로봇은 순간이동할 수 없고,
   다른 로봇 위로 튈 수도 있습니다.

2. **"안전 정지"가 실제로는 아무것도 안 했습니다.** 문제 발생 시 호출되는 `engage_fallback!` 함수가
   플래그 하나만 켰는데, **그 플래그를 읽는 코드가 시뮬레이터 어디에도 없었습니다.** 즉 "실패하면
   안전하게 멈춘다"는 보장이 이름뿐이었습니다.

### 만든 것

시뮬레이터의 **모든 속도 명령이 지나는 단 한 곳**에 필터를 넣었습니다. 로봇이 금지구역에 가까워질수록
그쪽 방향 속도 성분을 깎아, **애초에 들어가지 못하게** 합니다.

가장 중요한 성질: **"전부 정지"가 항상 실행 가능한 안전 행동임을 증명**했습니다. 속도를 0으로 두면
모든 안전 조건이 자동으로 만족되기 때문입니다. 이 증명 덕분에 "안전 정지"가 이름뿐이던 것에서
**실제로 작동하는 최후 수단**이 됐습니다.

외부 라이브러리를 추가하지 않았습니다(Julia 1.10 환경 보호). 2차원 최적화 문제라 정답을 직접 계산합니다.

### 검증

- **수학·동작 시험 18/18 통과** (완전탐색 대비 최적성 200문제, 오답 0건)
- **실제 빌드 2회: 성능 손실 0** — 완성 노드 수가 켜기 전과 정확히 같고, 6.8만 번의 속도 명령 중
  74~203번(0.1~0.3%)만 수정됨. "안전을 위해 로봇을 얼려버리는" 실패는 없었습니다.

> ⚠️ **정정**: "이 필터가 순간이동을 대체한다"는 제 주장은 **틀렸습니다.** 실험에서 필터를 켜도
> 순간이동 횟수가 줄지 않았습니다(양쪽 다 2회, 침범 깊이가 소수점 10자리까지 동일). 원인은 그 침범이
> **로봇이 이동해서 들어간 게 아니라, 구역이 주차된 로봇 위에 생성된 초기조건**이었기 때문입니다.
> 속도 필터는 이미 안에 있는 것을 순간에 꺼낼 수 없습니다(그게 물리적으로 옳습니다).
>
> 부수적으로 알게 된 사실: **기존 항법 스택에는 고칠 만한 동역학적 구역침범이 사실상 없습니다**
> (두 시나리오 모두 0회). 따라서 이 필터의 실제 가치는 "기존 위반 수정"이 아니라
> **"LLM이나 학습모델이 침묵하거나 틀려도 물리적 안전이 그와 독립적으로 성립한다"**는 점입니다.

## 5. 게이트 — 언제 비싼 플래너를 부를까

### 결과 (데이터 60개 기준)

부르는 횟수를 **똑같이 맞춰** 비교했습니다. 많이 부르면 손해가 줄어드는 건 당연하니, 같은 예산에서
누가 더 잘 고르는지를 봐야 신호가 진짜 정보를 담았는지 알 수 있습니다.

| 플래너 호출 비율 | 무작위(대조군) | 입력 낯섦도 | 결정 마진 | **모델 내부 이견** |
|---|---|---|---|---|
| 10% | 0.091 | 0.083 | 0.100 | **0.000** |
| 20% | 0.082 | **0.000** | 0.100 | **0.000** |
| 30% | 0.071 | **0.000** | 0.100 | **0.000** |
| 40% | 0.059 | **0.000** | 0.017 | **0.000** |
| 50% | 0.050 | **0.000** | 0.000 | **0.000** |

- **모델 내부 이견**: 5/5 예산에서 무작위보다 좋음. **10%만 불러도 손해 0** 달성.
- **입력 낯섦도**: 5/5에서 좋음. 20% 이상이면 손해 0.
- **결정 마진**: 2/5. 별로 쓸모없음.

> ⚠️ **정정**: 데이터 20개일 때 저는 "입력 낯섦도는 쓸모없다"고 보고드렸습니다(상관계수 −0.041,
> 방향까지 반대). **그 결론은 철회합니다.** 데이터 60개에서는 상관계수 −0.316, 분리도 +0.200으로
> 정상 작동합니다. **20개에서의 부정 결과는 "효과 없음"이 아니라 "판정 불가"였습니다.**
> 그때 함께 제시했던 설명 이론("표현이 좋아지면 낯섦도가 감지할 게 없어진다")도 근거 없음으로 철회합니다.

### 실행 경로에 연결 완료

> ⚠️ **정정**: 저는 "Julia에 배포된 모델이 선형(직선) 모델이라 나무가 없어서 이 신호를 못 만든다,
> 그래서 forest 내보내기가 1순위"라고 보고드렸습니다. **틀렸습니다.**
>
> - 배포 파일 `surrogate_linear.json`은 **이름과 달리 이미 60그루짜리 forest**입니다
>   (`meta.model = "RandomForest(60 x depth6)"`). 파일명이 옛날 이름 그대로 남아 있어 제가 오해했습니다.
> - Julia도 **이미 forest를 읽습니다** — `demo_surrogate_stream`이 나무별로 예측한 뒤 평균만 내고
>   있었습니다. 즉 필요한 재료가 전부 있는데 **평균을 내면서 "나무들이 갈리는가"라는 정보만 버리고
>   있었던 것**입니다.
>
> (다만 옛 데모 `demo_surrogate`는 선형 export만 읽고 forest면 에러를 냅니다. 제가 그 코드를 보고
> 잘못 일반화했습니다.)

그래서 이번에 실제로 붙였습니다:

- `surrogate_member_scores()` — 평균 내기 **전의** 나무별 점수를 그대로 돌려줍니다
- 결정 지점에서 게이트 판정을 계산·기록합니다 (`[GATE] 모델 내부 이견=... → ...`)
- 실제 배포된 60그루 forest로 동작 확인: 이견 0.25, 마진 0.521이 정상 계산됩니다

**판정과 집행은 일부러 분리해 뒀습니다.** 지금은 "확인이 필요하다"는 판정을 로그로 남기기만 하고,
실제로 진짜 플래너를 호출하는 배선은 하지 않았습니다 — 켜지도 않고 켰다고 말하지 않기 위해서입니다.

**→ 남은 일: 게이트가 "확인 권고"를 냈을 때 실제로 오라클을 호출하고 그 결과로 대응을 바꾸는 배선.**

## 8. 그 다음 단계 (2026-07-28 추가): "새 OOD 는 LLM, 아는 OOD 는 surrogate"

위 7절까지는 전부 **surrogate 한 개**의 이야기입니다. 목표 시스템은 두 producer 를 라우팅으로
엮는 것이고, 그건 여기 숫자들로는 증명되지 않습니다. 명제 4개로 쪼개면:

| | 명제 | 어디서 | 상태 |
|---|---|---|---|
| C1 | 처음 보는 종류에서 LLM > surrogate | `c1_novel_kind.py` | 하니스 완성 |
| C2 | 아는 종류에서 surrogate 가 동등품질·10⁴배 저렴 | 3절 LOIO + `cost_eval.py` | **측정 완료** |
| C3 | 낯섦을 스스로 판별해 라우팅 | `assimilation_stream.py` | 하니스 완성 |
| C4 | LLM 이 처리한 것을 학습해 다음부터 싸짐 | `assimilation_stream.py` | 하니스 완성 |

5절의 게이트 비교(입력낯섦도 / 결정마진 / 모델내부이견)는 **라우팅 대상이 플래너**였습니다.
C3 는 같은 게이트를 **LLM 으로** 라우팅하고, 같은 예산의 무작위 라우터를 이기는지로 채점합니다.

핵심 설계 변경 2가지 — 자세한 내용은 `md/DESIGN_ASSIMILATION.md`:

1. **LLM 입력이 자연어 문장이어야 한다.** 기존 LLM 실험은 `kind=battery, soc=0.55` 를 넣었는데
   이건 순환 논리입니다(새 사건엔 그 필드가 없음). 문장은 원래 `OOD_TRUTH_LOG` 에 있었고 덤프에만
   안 실렸습니다 → `gen_oracle_dataset.jl` 에 `nl`/`nl_source` 열 추가(가산적 패치).
   기존 60인스턴스 덤프는 `nl_events.py` 가 같은 템플릿으로 복원하고 `synthesized` 로 표시합니다.
2. **정적 LOKO 표로는 C3·C4 를 못 본다.** 주장이 "시간에 따른 전환"이라 스트림이 필요합니다.

**반드시 같이 읽을 상한**: 이 데이터셋은 fault/faultidle, zoneblk/zoneharm 에 일부러 같은 문장을
줍니다. 그래서 문장만 보는 producer 의 최고 성적은 regret 0 이 아니라 **0.100** 입니다
(`python nl_events.py <데이터>` 가 계산). 공교롭게 surrogate 의 LOKO regret 도 0.100 이므로,
`nl` 만으로는 원리적으로 못 이깁니다 → `nl+state` arm(문장 + 물리 서술자 6개)이 제안의 핵심입니다.
